# ЧАСТЬ 8 - Диски: подключение, хранилище Immich, бэкап, мониторинг

> **Что получится:**
> - диски опознаются по постоянным именам и не путаются после перестановки;
> - новый диск проверен, размечен и монтируется при загрузке, а его
>   отсутствие не мешает шлюзу загрузиться;
> - Immich хранит фото на нужном диске и не пишет мимо него, если диск
>   не примонтировался;
> - библиотеку Immich можно перенести на другой диск без потерь;
> - бэкап фото и базы - снимками, на другой диск, по расписанию;
> - SMART следит за всеми дисками, шумные диски спят.
>
> **Правила для ИИ - в Части 0.** Все команды - **на шлюзе** (там, где
> стоят диски и Immich). ⛔ Шаг 8.3 **стирает диск**: перед ним СТОП и
> подтверждение по серийному номеру.

---

## Шаг 8.0 - Роли дисков (продумать до покупки и подключения)

| Роль | Какой диск | Почему |
|---|---|---|
| система | SSD | шлюз, скрипты, база Immich (`DB_DATA_LOCATION`) |
| **фото Immich** | самый здоровый и **тихий** | к нему обращаются каждый раз при просмотре фото |
| бэкап фото | **другой** физический диск | копия на том же диске - не копия |
| редкий/шумный диск | под бэкапы раз в неделю, со сном (8.9) | шум и износ только во время бэкапа |
| копия вне дома | по желанию (VPS, облако, диск у родственников) | пожар, кража, скачок напряжения |

Главные принципы:
- **база Immich - на SSD**, не на HDD и не на сетевой папке: на медленном
  диске интерфейс тормозит, на сетевой папке база может повредиться;
- диск для фото выбирай по SMART (8.2), а не по возрасту или бренду;
- указывай диски **только по постоянным именам**: `UUID` в `fstab`,
  `/dev/disk/by-id/...` в `smartd`, `hd-idle` и скриптах. Буквы `sda/sdb`
  меняются, когда добавляешь или переставляешь диск.

> ⚠️ **Реальный случай:** добавили диск - буквы сдвинулись. Мониторинг SMART
> был настроен на `/dev/sdb` и молча начал следить за другим диском, три
> диска остались без присмотра.

## Шаг 8.1 - Опознать диски

```
lsblk -o NAME,SIZE,MODEL,SERIAL,FSTYPE,LABEL,MOUNTPOINT
```

**ОЖИДАЕТСЯ:** список дисков с моделью и серийным номером. Новый диск - тот,
у которого нет точки монтирования (`MOUNTPOINT` пуст). Если на нём разделы
`ntfs`/`vfat` - он из-под Windows, там могут быть чужие данные.

Постоянные имена дисков:

```
ls -l /dev/disk/by-id/ | grep ata- | grep -v part
```

**ОЖИДАЕТСЯ:** строки вида
`ata-МОДЕЛЬ_СЕРИЙНИК -> ../../sdX`. Дальше в этой части диск называется
`ata-МОДЕЛЬ_СЕРИЙНИК` - ⛔ везде подставляй своё имя из этого вывода.

> Сверь серийный номер с наклейкой на диске - так ты точно знаешь, какой
> физический диск какой.

## Шаг 8.2 - Проверить здоровье диска

```
sudo smartctl -a /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК | tee /tmp/smart-new.log
```

Смотри в таблице атрибутов столбец `RAW_VALUE`:

| Атрибут | Норма | Плохо |
|---|---|---|
| `5 Reallocated_Sector_Ct` | 0 | любое значение больше 0 и растёт |
| `197 Current_Pending_Sector` | 0 | больше 0 - сектора, которые не читаются |
| `198 Offline_Uncorrectable` | 0 | больше 0 |
| `199 UDMA_CRC_Error_Count` | 0 | растёт - кабель SATA, а не диск |
| `183 Runtime_Bad_Block` (если есть) | 0 | больше 0 - настораживает |
| `9 Power_On_Hours` | - | наработка в часах, для сравнения дисков |
| `193 Load_Cycle_Count` | - | парковки головок; у ноутбучных дисков большие числа нормальны |
| `194 Temperature_Celsius` | до ~45 | выше 50 - нужен обдув |

Ещё: строка `SMART overall-health ... PASSED` и раздел `SMART Error Log` -
`No Errors Logged`.

> ⚠️ У некоторых производителей (HGST, Seagate) "сырые" значения 187/188
> огромные: это упакованные служебные поля, а не счётчик ошибок. Смотри
> вместе с остальными признаками.

Полный тест поверхности - ничего не стирает, идёт часами в фоне:

```
sudo smartctl -t long /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК
```

**ОЖИДАЕТСЯ:** `Testing has begun` и время окончания. Результат после
окончания:

```
sudo smartctl -l selftest /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК
```

**ОЖИДАЕТСЯ:** `Extended offline  Completed without error`.

**ЕСЛИ `Completed: read failure`** -> диск с битыми секторами. Под фото и
бэкапы не годится.

## Шаг 8.3 - Разметить и отформатировать (⛔ СТИРАЕТ ДИСК)

⛔ **СТОП.** Этот шаг уничтожает **всё** на диске. Перед ним:
1. серийный номер в имени `ata-...` совпадает с наклейкой нового диска;
2. на диске нет нужных данных (старые фото, документы с ноутбука);
3. диск не смонтирован:

```
lsblk -o NAME,SERIAL,MOUNTPOINT /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК
```

**ОЖИДАЕТСЯ:** столбец `MOUNTPOINT` пуст у диска и всех его разделов.

Только после подтверждения человека. Стереть старые подписи разделов:

```
sudo wipefs -a /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК
```

Новая таблица разделов и один раздел на весь диск:

```
sudo parted -s /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК mklabel gpt mkpart data ext4 1MiB 100%
```

```
sudo partprobe
```

Файловая система с понятной меткой (⛔ метку придумай по роли: `photos`,
`backup`):

```
sudo mkfs.ext4 -L photos /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК-part1
```

**ОЖИДАЕТСЯ:** `Writing superblocks ... done`.

> Метка - только для удобства человека. Монтируем всё равно по `UUID`
> (8.4): метки остаются от старых ролей и со временем врут.

## Шаг 8.4 - Монтировать при загрузке

UUID нового раздела:

```
sudo blkid /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК-part1
```

**ОЖИДАЕТСЯ:** `UUID="xxxxxxxx-xxxx-..."`. Скопируй значение без кавычек.

Папка, куда монтировать (⛔ имя по роли):

```
sudo mkdir -p /mnt/photos
```

Бэкап `fstab`:

```
sudo cp /etc/fstab /etc/fstab.bak-disk
```

Строка монтирования (⛔ подставь UUID и папку):

```
echo 'UUID=ПОДСТАВЬ_UUID /mnt/photos ext4 defaults,nofail,x-systemd.device-timeout=15s 0 2' | sudo tee -a /etc/fstab
```

> - `nofail` - если диск умер или отключён, шлюз **всё равно загрузится**
>   (без этого он встанет в аварийный режим, а дом без интернета);
> - `x-systemd.device-timeout=15s` - не ждать отсутствующий диск полторы
>   минуты;
> - последняя `2` - проверка файловой системы при загрузке.

```
sudo systemctl daemon-reload
```

```
sudo mount -a
```

**ОЖИДАЕТСЯ:** пустой вывод. Ошибка - опечатка в строке, исправь
`sudo nano /etc/fstab`.

```
findmnt /mnt/photos
```

**ОЖИДАЕТСЯ:** строка с `/mnt/photos`, устройством и `ext4`.

```
df -h /mnt/photos
```

**ОЖИДАЕТСЯ:** размер нового диска, а **не** системного SSD.

### 8.4.1 - Docker ждёт диск (защита от записи мимо диска)

⚠️ **Реальная грабля:** диск монтировался позже, чем стартовали контейнеры.
Immich видел пустую папку: фото не открывались (`ENOENT`), а новые загрузки
могли лечь на **системный SSD** в пустую точку монтирования и забить его.

Заставим Docker стартовать только после того, как диск смонтирован
(⛔ подставь папку; если дисков с данными Immich несколько - через пробел):

```
sudo mkdir -p /etc/systemd/system/docker.service.d
```

```
printf '[Unit]\nRequiresMountsFor=/mnt/photos\n' | sudo tee /etc/systemd/system/docker.service.d/wait-disks.conf
```

```
sudo systemctl daemon-reload
```

```
systemctl show docker -p RequiresMountsFor
```

**ОЖИДАЕТСЯ:** `RequiresMountsFor=/mnt/photos`.

> Обратная сторона: если диск умер, Docker не запустится вовсе (все
> контейнеры, не только Immich). Это сознательный выбор - лучше заметная
> остановка, чем тихая запись фото не туда. Шлюз и интернет при этом
> работают.

## Шаг 8.6 - Перенести библиотеку Immich на другой диск

Когда: новый диск здоровее, тише или больше текущего.

**1. Где библиотека сейчас** (это источник правды, а не память):

```
sudo docker inspect immich_server --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}'
```

**ОЖИДАЕТСЯ:** путь, например `/mnt/old/immich`. Дальше он - `СТАРЫЙ_ПУТЬ`.

```
grep -E '^(UPLOAD_LOCATION|DB_DATA_LOCATION)=' ~/immich/.env
```

> Если `DB_DATA_LOCATION` тоже на старом диске - переноси базу вместе с фото
> (тем же способом, пока Immich остановлен). Если база в `./postgres`
> (на SSD) - её не трогаем.

**2. Хватит ли места:**

```
sudo du -sh СТАРЫЙ_ПУТЬ
```

```
df -h /mnt/photos
```

**ОЖИДАЕТСЯ:** свободно на новом диске заметно больше, чем занимает
библиотека.

**3. Остановить Immich** (во время копирования в библиотеку ничего не должно
писаться):

```
cd ~/immich && sudo docker compose down
```

**4. Копировать.** ⛔ Косые черты в конце путей **обязательны**: без них
папка скопируется внутрь новой папки ещё одним уровнем.

```
sudo rsync -aHAX --numeric-ids --info=progress2 СТАРЫЙ_ПУТЬ/ /mnt/photos/immich/
```

**ОЖИДАЕТСЯ:** прогресс до 100% без ошибок. На сотнях гигабайт - часы.

**5. Проверить, что копия полная** - пробный прогон, ничего не меняет:

```
sudo rsync -aHAXn --numeric-ids --itemize-changes СТАРЫЙ_ПУТЬ/ /mnt/photos/immich/ | head
```

**ОЖИДАЕТСЯ:** пустой вывод (копировать больше нечего). Есть строки -
повтори шаг 4.

**6. Переключить Immich на новый путь:**

```
cp ~/immich/.env ~/immich/.env.bak-move
```

```
sed -i 's|^UPLOAD_LOCATION=.*|UPLOAD_LOCATION=/mnt/photos/immich|' ~/immich/.env
```

```
grep '^UPLOAD_LOCATION=' ~/immich/.env
```

**ОЖИДАЕТСЯ:** `UPLOAD_LOCATION=/mnt/photos/immich`.

Если в 8.4.1 Docker ждал старый диск - поправь путь в
`/etc/systemd/system/docker.service.d/wait-disks.conf` и выполни
`sudo systemctl daemon-reload`.

**7. Запустить и проверить:**

```
cd ~/immich && sudo docker compose up -d
```

```
sudo docker inspect immich_server --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}'
```

**ОЖИДАЕТСЯ:** `/mnt/photos/immich`.

В браузере: открываются старые фото (полный размер, не только превью),
загружается новое тестовое фото.

**8. Поправить бэкап:** в скрипте бэкапа (8.7) переменная `SRC` - на новый
путь. Иначе бэкап остановится с ошибкой (так задумано, см. 8.7).

**9. Старую копию** не удалять 1-2 недели. Чтобы случайно не начать писать в
неё, переименуй:

```
sudo mv СТАРЫЙ_ПУТЬ СТАРЫЙ_ПУТЬ.old-$(date +%F)
```

Через пару недель, если всё работает, - удалить её.

## Шаг 8.7 - Бэкап Immich снимками

Как устроено:
- каждый снимок - полная копия библиотеки в папке с датой, но неизменённые
  файлы **не копируются заново** (жёсткие ссылки `--link-dest`): десять
  снимков занимают почти как один плюс изменения;
- удалённое по ошибке фото остаётся в старых снимках, хранится `KEEP`
  последних;
- база выгружается дампом в снимок и отдельно на системный SSD;
- нет новых файлов и база не менялась - бэкап пропускается, диск бэкапов
  не будится;
- **защита от главной грабли:** источник берётся только если это та самая
  папка, которую реально использует контейнер.

> ⚠️ **Реальная грабля:** бэкап `rsync --delete` с перепутанными источником и
> целью каждую ночь откатывал живую библиотеку к старой копии. Направление
> здесь одно: **живая библиотека -> снимки**, никогда наоборот.

⛔ Подставь `SRC` (папка библиотеки, как в 8.6 п.1), `DST` (папка снимков на
**другом** диске) и `QUIET_FROM/QUIET_TO` (часы, когда бэкап не будит шумный
диск; не нужно - поставь `QUIET_FROM=24; QUIET_TO=0`).

```
sudo tee /usr/local/sbin/backup-immich.sh > /dev/null <<'EOF'
#!/bin/bash
# backup-immich.sh - бэкап Immich: живая библиотека -> снимки на другом диске.
# Запуск: sudo backup-immich.sh [--force]
set -u
SRC=/mnt/photos/immich            # живая библиотека (UPLOAD_LOCATION)
DST=/mnt/backup/immich-snap       # снимки - на ДРУГОМ диске
DBLOCAL=/var/backups/immich-db    # последний дамп базы - на системном SSD
KEEP=8                            # сколько снимков хранить
QUIET_FROM=21; QUIET_TO=9         # в эти часы не запускаться (шумный диск)
LOG=/var/log/backup-immich.log
STATE=/var/lib/backup-immich
FORCE=0; [ "${1:-}" = "--force" ] && FORCE=1

log(){ echo "$(date '+%F %T') $*" | tee -a "$LOG"; }
tg(){ [ -x /usr/local/sbin/tg-notify.sh ] && /usr/local/sbin/tg-notify.sh "Бэкап Immich" "$1" "$2"; }
fail(){ log "ERROR: $*"; tg "ОШИБКА: $* (лог $LOG)" warn; exit 1; }

h=$((10#$(date +%H)))
if [ "$FORCE" -eq 0 ] && { [ "$h" -ge "$QUIET_FROM" ] || [ "$h" -lt "$QUIET_TO" ]; }; then
  log "тихие часы ($h ч) - пропуск"; exit 0
fi

mountpoint -q "$(dirname "$SRC")" || fail "диск библиотеки $(dirname "$SRC") не примонтирован"
mountpoint -q "$(dirname "$DST")" || fail "диск бэкапа $(dirname "$DST") не примонтирован"
LIVE=$(docker inspect immich_server --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}' 2>/dev/null)
[ "$LIVE" = "$SRC" ] || fail "живая библиотека Immich '$LIVE' != SRC '$SRC' - поправь SRC"
mkdir -p "$DST" "$DBLOCAL" "$STATE"

log "=== старт ==="
TMP="$DBLOCAL/new.sql"
docker exec immich_postgres pg_dumpall -U postgres > "$TMP" 2>>"$LOG" || fail "дамп базы"
[ -s "$TMP" ] || fail "дамп базы пустой"
NEWMD5=$(md5sum < "$TMP" | cut -d' ' -f1)
OLDMD5=$(cat "$STATE/db.md5" 2>/dev/null)

if [ -f "$STATE/last-ok" ] && [ "$FORCE" -eq 0 ]; then
  NEWF=$(find "$SRC" -newer "$STATE/last-ok" -type f -print -quit 2>/dev/null)
  if [ -z "$NEWF" ] && [ "$NEWMD5" = "$OLDMD5" ]; then
    rm -f "$TMP"; log "изменений нет - пропуск"; exit 0
  fi
fi

SNAP="$DST/$(date +%F_%H%M)"
LATEST=$(ls -1d "$DST"/20??-??-??_???? 2>/dev/null | tail -1)
log "снимок $SNAP${LATEST:+ (от $LATEST)}"
rsync -aAX --delete ${LATEST:+--link-dest="$LATEST"} "$SRC/" "$SNAP.partial/" >>"$LOG" 2>&1
rc=$?
[ "$rc" -eq 0 ] || [ "$rc" -eq 24 ] || fail "rsync rc=$rc"
mkdir -p "$SNAP.partial/_db"
gzip -c "$TMP" > "$SNAP.partial/_db/immich-db.sql.gz" || fail "gzip дампа"
mv "$SNAP.partial" "$SNAP" || fail "переименование снимка"

[ -f "$DBLOCAL/latest.sql.gz" ] && mv -f "$DBLOCAL/latest.sql.gz" "$DBLOCAL/previous.sql.gz"
gzip -c "$TMP" > "$DBLOCAL/latest.sql.gz"; rm -f "$TMP"

ls -1d "$DST"/20??-??-??_???? | head -n -"$KEEP" | while read -r old; do
  rm -rf -- "$old" && log "удалён старый снимок $old"
done
rm -rf "$DST"/*.partial 2>/dev/null

echo "$NEWMD5" > "$STATE/db.md5"; touch "$STATE/last-ok"
N=$(ls -1d "$DST"/20??-??-??_???? | wc -l)
log "=== готово: снимков $N ==="
tg "Готово, снимок $(basename "$SNAP"), всего снимков $N" info
exit 0
EOF
```

> `--delete` здесь безопасен: он чистит только **новый** снимок
> (`$SNAP.partial`), который сам же и создаёт. Живую библиотеку скрипт
> только читает.
>
> Скрипт проверяет, что `SRC` и `DST` лежат прямо в точках монтирования
> (`/mnt/photos/immich` -> `/mnt/photos`). Если у тебя глубже - поправь
> строки `mountpoint`.

```
sudo chmod 755 /usr/local/sbin/backup-immich.sh
```

```
sudo bash -n /usr/local/sbin/backup-immich.sh && echo "СИНТАКСИС OK"
```

Первый запуск вручную (первый снимок - полная копия, долго):

```
sudo /usr/local/sbin/backup-immich.sh --force
```

**ОЖИДАЕТСЯ:** `снимок ...`, затем `=== готово: снимков 1 ===`.

**ЕСЛИ `живая библиотека ... != SRC`** -> в `SRC` не та папка. Не
"исправляй" проверку - поправь `SRC` по выводу 8.6 п.1.

Расписание - раз в неделю, в понедельник в 11:00 (днём: шумный диск ночью
не будит):

```
sudo tee /etc/systemd/system/backup-immich.service > /dev/null <<'EOF'
[Unit]
Description=Immich backup (DB + media snapshots)
After=docker.service local-fs.target

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/backup-immich.sh
Nice=19
IOSchedulingClass=idle
EOF
```

```
sudo tee /etc/systemd/system/backup-immich.timer > /dev/null <<'EOF'
[Unit]
Description=Immich backup weekly (Mon 11:00)

[Timer]
OnCalendar=Mon *-*-* 11:00:00
Persistent=true

[Install]
WantedBy=timers.target
EOF
```

```
sudo systemctl daemon-reload
```

```
sudo systemctl enable --now backup-immich.timer
```

```
systemctl list-timers backup-immich.timer --no-pager
```

**ОЖИДАЕТСЯ:** ближайший понедельник, 11:00.

### 8.7.1 - Восстановить файлы из снимка

Одно фото или папку - просто скопировать из снимка обратно:

```
ls /mnt/backup/immich-snap/
```

Найди нужный файл в снимке по дате и скопируй его на ПК или в папку
загрузки. Immich подхватит файл, если загрузить его заново через приложение
или веб-интерфейс.

⛔ **Вся библиотека целиком** из снимка - только при полной потере, только с
остановленным Immich и только после подтверждения человека. Направление:
снимок -> живая папка. База восстанавливается из `_db/immich-db.sql.gz` по
[инструкции Immich](https://docs.immich.app/administration/backup-and-restore).

### 8.7.2 - Второй снимок на другой диск (каждую ночь)

Недельный снимок на шумный диск оставляет риск: всё загруженное за неделю
лежит в одном экземпляре. Реальный случай (ноябрь 2026): диск с живой
библиотекой выдал битые сектора, а последний снимок был недельной давности.
Решение - ночной снимок на **третий** диск (тихий), недельный остаётся.

Ночной скрипт - копия недельного с другими путями, делается одной командой.
⛔ Подставь `ПОДСТАВЬ_ДИСК_НОЧНОЙ` - точку монтирования третьего диска
(например `/mnt/500gbM`). Это **не** диск живой библиотеки и не диск
недельных снимков.

```
sudo sed -e 's|^DST=.*|DST=ПОДСТАВЬ_ДИСК_НОЧНОЙ/immich-snap|' -e 's|^LOG=.*|LOG=/var/log/backup-immich-daily.log|' -e 's|^DBLOCAL=.*|DBLOCAL=/var/backups/immich-db-daily|' -e 's|^STATE=.*|STATE=/var/lib/backup-immich-daily|' -e 's|^KEEP=.*|KEEP=7|' -e 's|^QUIET_FROM=.*|QUIET_FROM=24; QUIET_TO=0|' -e '/tg "Готово/d' -e 's|"Бэкап Immich"|"Бэкап Immich (ночной)"|' /usr/local/sbin/backup-immich.sh | sudo tee /usr/local/sbin/backup-immich-daily.sh > /dev/null
```

Что делает команда: снимки - на третий диск, свой лог, состояние и папка
дампа (с недельным не пересекаются), 7 снимков, без тихих часов, без
ежедневного "Готово" в Telegram (ошибки по-прежнему приходят).

Проверка: ожидаются новые `DST`, `LOG`, `DBLOCAL`, `STATE`, `KEEP=7`,
`QUIET_FROM=24`, ни одной строки с `Готово` и `SYNTAX-OK`:

```
sudo chmod 755 /usr/local/sbin/backup-immich-daily.sh; grep -nE '^(DST|LOG|DBLOCAL|STATE|KEEP|QUIET_FROM)=|Готово' /usr/local/sbin/backup-immich-daily.sh; bash -n /usr/local/sbin/backup-immich-daily.sh && echo SYNTAX-OK
```

⛔ В скрипте есть проверка `mountpoint -q` для диска снимков. Если она
указывает на диск недельных снимков - поправь на `ПОДСТАВЬ_ДИСК_НОЧНОЙ`:

```
grep -n 'mountpoint -q' /usr/local/sbin/backup-immich-daily.sh
```

Служба и таймер (каждую ночь в 03:30):

```
sudo tee /etc/systemd/system/backup-immich-daily.service > /dev/null <<'EOF'
[Unit]
Description=Immich nightly snapshot
After=docker.service

[Service]
Type=oneshot
Nice=10
IOSchedulingClass=idle
ExecStart=/usr/local/sbin/backup-immich-daily.sh
EOF
```

```
sudo tee /etc/systemd/system/backup-immich-daily.timer > /dev/null <<'EOF'
[Unit]
Description=Immich nightly snapshot (03:30)

[Timer]
OnCalendar=*-*-* 03:30:00
Persistent=true

[Install]
WantedBy=timers.target
EOF
```

⛔ Именно `enable --now`. Просто `enable` запустит таймер только после
следующей перезагрузки (реальная ошибка при настройке):

```
sudo systemctl daemon-reload && sudo systemctl enable --now backup-immich-daily.timer && systemctl list-timers backup-immich-daily.timer --no-pager | sed -n '2p'
```

**ОЖИДАЕТСЯ:** строка со следующим запуском в 03:30.

Первый снимок копирует библиотеку целиком (на 90 ГБ - около 25 минут),
следующие - только изменения:

```
sudo systemctl start --no-block backup-immich-daily.service
```

```
tail -3 /var/log/backup-immich-daily.log
```

**ОЖИДАЕТСЯ** (по окончании): `=== готово: снимков 1 ...`.

### 8.7.3 - Проверить, что бэкап настоящий

Бэкап, который ни разу не проверяли, - надежда, а не бэкап. Две проверки,
обе только читают.

**1. Число файлов** в последнем снимке и в живой библиотеке. ⛔ Подставь
`ПОДСТАВЬ_SRC` (живая библиотека) и `ПОДСТАВЬ_DST` (папка снимков):

```
L=$(ls -1d ПОДСТАВЬ_DST/20??-??-??_???? | tail -1); echo "снимок: $L"; echo "библиотека: $(sudo find ПОДСТАВЬ_SRC -type f | wc -l)"; echo "снимок:     $(sudo find "$L" -type f | wc -l)"
```

**ОЖИДАЕТСЯ:** числа совпадают или отличаются на единицы (фото, загруженные
или удалённые после снимка). В снимке заметно меньше - ⛔ СТОП, бэкап
неполный, разбирать лог бэкапа.

**2. Пробное восстановление:** 20 случайных файлов из снимка сравниваются
по содержимому (md5) с живыми:

```
L=$(ls -1d ПОДСТАВЬ_DST/20??-??-??_???? | tail -1); sudo find "$L" -type f -not -path '*/_db/*' | shuf -n 20 | while read -r f; do r=${f#"$L"/}; if [ "$(sudo md5sum < "$f")" = "$(sudo md5sum < "ПОДСТАВЬ_SRC/$r" 2>/dev/null)" ]; then echo "OK   $r"; else echo "РАЗН $r"; fi; done | sort | uniq -c -w4
```

**ОЖИДАЕТСЯ:** `20 OK`. Единичный `РАЗН` бывает у файла, который Immich
поменял после снимка (миниатюры). Много `РАЗН` - ⛔ СТОП, снимок испорчен.

Сделать обе проверки после настройки и потом раз в месяц-два.

## Шаг 8.9 - Сон шумного диска (`hd-idle`)

Для диска бэкапов: через 10 минут простоя останавливает шпиндель.

```
sudo apt install -y hd-idle
```

```
sudo cp -n /etc/default/hd-idle /etc/default/hd-idle.bak
```

⛔ Подставь by-id **именно шумного** диска:

```
printf 'START_HD_IDLE=true\nHD_IDLE_OPTS="-i 0 -a /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК -i 600 -c ata"\n' | sudo tee /etc/default/hd-idle
```

> - `-i 0` первым - остальные диски **не трогать**. ⚠️ Реальный случай: без
>   него `-i 600` стало правилом для **всех** дисков - засыпал диск с фото
>   Immich, а длинный SMART-тест нового диска двое суток стоял на месте
>   (в сне тест на паузе). Разбудить диск: прочитать 1 МБ через `dd ... iflag=direct`;
> - `-a ... -i 600` - этот диск спит после 600 с простоя;
> - `-c ata` - команда остановки для SATA (без неё часть дисков не засыпает).

```
sudo systemctl restart hd-idle
```

Проверка через 10+ минут без обращений к диску:

```
sudo hdparm -C /dev/disk/by-id/ata-МОДЕЛЬ_СЕРИЙНИК
```

**ОЖИДАЕТСЯ:** `drive state is: standby`.

> `smartd` с опцией `-n standby,q` (Часть 4, раздел 11) спящий диск не
> будит. ⚠️ Не ставь сон диску с **фото Immich**: каждый просмотр будет
> ждать раскрутки по несколько секунд, а частые старты изнашивают диск.

### 8.9.1 - Кто будит спящий диск

Журнал `hd-idle` пишет каждую остановку и раскрутку:

```
sudo journalctl -u hd-idle --since "-3d" --no-pager | grep -iE 'spindown|spinup' | tail -20
```

Раскрутки в одно и то же время каждый день -> ищи таймер с этим временем:

```
systemctl list-timers --all --no-pager
```

**Реальный случай:** диск бэкапов просыпался каждый день в 12:00, хотя бэкап
делался раз в 10 дней. Скрипт бэкапа запускался ежедневно и, чтобы узнать
дату последнего снимка, делал `find` по самому диску - уже этого хватало для
раскрутки. Лечение: хранить дату последнего снимка **на системном SSD** и
проверять её **до** любого обращения к диску бэкапов.

Шаблон (вставить в скрипт бэкапа до проверки `mountpoint`; `log`, `FORCE`,
`MIN_INTERVAL_DAYS` должны быть объявлены выше):

```
STATE=/var/lib/ИМЯ-БЭКАПА.last   # дата последнего снимка - на SSD
if [ "$FORCE" -ne 1 ] && [ -f "$STATE" ]; then
    S_DATE=$(cat "$STATE")
    S_EPOCH=$(date -d "$S_DATE" +%s 2>/dev/null || echo 0)
    S_AGE=$(( ($(date +%s) - S_EPOCH) / 86400 ))
    if [ "$S_AGE" -lt "$MIN_INTERVAL_DAYS" ]; then
        log "Метка на SSD: последний снимок $S_DATE ($S_AGE дн. назад) - пропускаю, диск не будим"
        exit 0
    fi
fi
```

И после успешного снимка (рядом с `log "Снимок готов..."`):

```
echo "$DATE" > "$STATE"
```

Первый запуск после правки один раз заглянет на диск: в старой проверке по
диску тоже добавь `echo "$LAST_DATE" > "$STATE"`, и метка появится сама.
**ПРОВЕРКА:** второй ручной запуск пишет `Метка на SSD: ... диск не будим`.

## Шаг 8.10 - Диск начал умирать: что делать

Признаки: в Telegram пришло сообщение от SMART; растут `Reallocated`,
`Pending`, `Uncorrectable`; длинный тест падает с `read failure`; в журнале
ядра ошибки ввода-вывода:

```
sudo journalctl -k --since "-7d" --no-pager | grep -iE "I/O error|ata[0-9].*(error|failed)" | tail -20
```

Порядок:
1. **Сначала данные.** Если это диск с фото - убедись, что последний снимок
   бэкапа свежий (`tail -5 /var/log/backup-immich.log`), при необходимости
   сделай внеочередной: `sudo /usr/local/sbin/backup-immich.sh --force`.
2. Перенеси библиотеку на здоровый диск (8.6).
3. Убери умирающий диск **отовсюду**, где он упомянут, до того как вынуть:
   - строку из `/etc/fstab` (с бэкапом файла);
   - строку из `/etc/smartd.conf`, затем `sudo systemctl restart smartd`;
   - из `/etc/default/hd-idle`, если он там был;
   - из `RequiresMountsFor` в `docker.service.d/wait-disks.conf`;
   - из скриптов бэкапа (`SRC`/`DST`).
4. Выключить шлюз, вынуть диск.

> Благодаря `nofail` (8.4) шлюз загрузится, даже если забыл убрать строку
> из `fstab`, - но лучше не оставлять мусор.

### 8.10.1 - SMART: "тест упал с read failure" - разобрать по шагам

Реальный случай (ноябрь 2026, б/у ноутбучный диск 2.5" с фото): ночной
длинный тест - `Completed: read failure` на одном адресе. Дальше по порядку,
ничего не меняя, пока не дойдём до шага 5. ⛔ Подставь в команды
`ПОДСТАВЬ_ДИСК` - постоянное имя `/dev/disk/by-id/ata-...` (раздел 8.1).

**1. Счётчики и адрес ошибки:**

```
sudo smartctl -a ПОДСТАВЬ_ДИСК 2>&1 | grep -E '^ *(5|187|197|198|199) |# 1 |# 2 |LBA_of_first' | tee /tmp/smart-fail.log
```

| Счётчик | Что значит |
|---|---|
| 5 Reallocated | сектора уже подменены запасными |
| 197 Pending | нечитаемые, ждут перезаписи |
| 198 Uncorrectable | не прочитались при самопроверке |
| 199 UDMA_CRC | ошибки **кабеля**, не диска: растёт - менять SATA-кабель, диск цел |

`LBA_of_first_error` в строке `# 1` - номер плохого сектора (дальше `LBA`).

**2. Прочитать это место напрямую** (⛔ подставь `LBA`, команда только читает):

```
sudo dd if=ПОДСТАВЬ_ДИСК of=/dev/null bs=512 skip=$((ПОДСТАВЬ_LBA-440)) count=2048 iflag=direct 2>&1 | head -1
```

`2048+0 records in` - место читается. Меньше, с `Input/output error` -
сектор действительно битый.

**3. Что лежит в этом месте.** Нужны начало раздела и размер блока:

```
lsblk -o NAME,START,MOUNTPOINT ПОДСТАВЬ_ДИСК
```

```
sudo tune2fs -l ПОДСТАВЬ_ДИСК-part1 | grep 'Block size'
```

Номер блока файловой системы = `(LBA − START) / (BlockSize / 512)`. Для
блока 4096: `(LBA − START) / 8`.

```
sudo debugfs -R "icheck ПОДСТАВЬ_БЛОК" ПОДСТАВЬ_ДИСК-part1
```

- `<block not found>` - место **свободное**, ни одного файла не задето;
- число - номер inode. Имя файла: `sudo debugfs -R "ncheck ЧИСЛО" ПОДСТАВЬ_ДИСК-part1`.
  ⛔ СТОП: сначала восстанови этот файл из снимка (8.7.1), потом шаг 5.

**4. Вся поверхность** - проверка только чтением, отдельной службой
(обрыв SSH её не остановит, на 500 ГБ около 1.5-2 ч):

```
sudo systemd-run --unit=badblocks-check badblocks -b 4096 -c 64 -v -o /root/badblocks.txt ПОДСТАВЬ_ДИСК
```

Прогресс:

```
p=$(pgrep -x badblocks); r=$(sudo awk '/read_bytes/{print $2}' /proc/$p/io); echo "прочитано $((r/1073741824)) ГБ"
```

⛔ Не `sudo wc -l < /root/badblocks.txt`: перенаправление `<` выполняется
без прав root ("Отказано в доступе"). Правильно:

```
sudo wc -l /root/badblocks.txt
```

Номера в файле - от начала **диска** в блоках по 4096. Номер блока
файловой системы = `номер − START/8`. Проверить все разом:

```
for b in $(sudo cat /root/badblocks.txt); do echo "icheck $((b-ПОДСТАВЬ_START/8))"; done > /tmp/icheck.cmd; sudo debugfs -f /tmp/icheck.cmd ПОДСТАВЬ_ДИСК-part1 2>/dev/null | grep -v Block
```

**5. Перезаписать свободные плохие места** - диск сам подменит сектора
запасными. Перед каждой записью команда ещё раз проверяет, что блок
свободен (Immich мог его занять), занятые не трогает:

```
for b in $(sudo cat /root/badblocks.txt); do sudo debugfs -R "icheck $((b-ПОДСТАВЬ_START/8))" ПОДСТАВЬ_ДИСК-part1 2>/dev/null | grep -q 'not found' && sudo dd if=/dev/zero of=ПОДСТАВЬ_ДИСК bs=4096 count=1 seek=$b oflag=direct conv=notrunc status=none && echo "перезаписан $b"; done
```

После - снова шаг 1: `197 Pending` должен уменьшиться.

**6. Решение:**

| Картина | Решение |
|---|---|
| один сектор, после перезаписи всё читается, повторный badblocks чистый | диск в работе, следить по SMART |
| плохие места кучкой в одном участке, после перезаписи участок снова не читается | участок деградирует - живые данные с диска уводить (8.6), диск - только под дополнительную копию |
| счётчики растут день ото дня, ошибки в разных местах | диск умирает - 8.10, вынимать |

> В реальном случае было "кучкой": 12 плохих блоков в участке 17 МБ, после
> перезаписи участок снова не прочитался. Живую библиотеку перенесли на
> другой диск (8.6), а старый диск оставили под ночные снимки (8.7.2).

**7. Если диск оставлен под копии - запретить файловой системе плохие места.**
Перезапись не помогла, сектора остались "ожидающими" - пусть ext4 сама
обходит их стороной. `e2fsck -c` читает весь раздел (только чтение) и вносит
нечитаемые блоки в список плохих блоков ФС. Раздел на это время (1.5-2 ч на
500 ГБ) отмонтирован, запускать отдельной службой:

```
sudo umount /mnt/ПОДСТАВЬ_ТОЧКА
```

```
sudo systemd-run --unit=e2fsck-bad e2fsck -f -c -y ПОДСТАВЬ_ДИСК-part1
```

Уведомление в Telegram по окончании (не нужно сидеть и проверять):

```
sudo systemd-run --unit=e2fsck-notify sh -c 'while systemctl is-active -q e2fsck-bad; do sleep 60; done; /usr/local/sbin/tg-notify.sh "Проверка диска" "e2fsck закончил" info'
```

```
journalctl -u e2fsck-bad --no-pager | tail -20
```

**ОЖИДАЕТСЯ:** `Updating bad block inode`, проходы 1-5, `FILE SYSTEM WAS MODIFIED`.
Служба при этом "failed" - ⚠️ это не ошибка: e2fsck отдаёт код 1, когда что-то
исправил. Список плохих блоков ФС:

```
sudo dumpe2fs -b ПОДСТАВЬ_ДИСК-part1
```

```
sudo systemctl reset-failed e2fsck-bad; sudo mount /mnt/ПОДСТАВЬ_ТОЧКА
```

Счётчик `197 Pending` в SMART при этом НЕ обнулится - это память диска. Чтобы
smartd писал в Telegram только о НОВЫХ плохих секторах, а не напоминал о
старых, в строке этого диска в `/etc/smartd.conf` после `-a` добавить
`-C 197+ -U 198+` (сначала копия файла), затем
`sudo systemctl restart smartmontools`. Пришло новое сообщение про этот
диск - он деградирует дальше, менять.

> В реальном случае через два дня после перезаписи e2fsck нашёл уже только
> 2 плохих блока из прежних 12 - часть мест перезапись всё же вылечила.

> Самотест SMART может долго стоять на "90% remaining" - это не зависание
> диска, а то, что он пропускает тест при обращениях. badblocks нагляднее.

## Шаг 8.11 - Запасная загрузочная флешка (система на зеркале RAID1)

Нужна там, где система стоит на программном зеркале (`md0` из двух SSD), а
прошивка материнской платы при смерти одного SSD **не переходит** сама на
второй ("no boot device"). Флешка с загрузчиком стоит в порядке загрузки
первой и грузит систему с того SSD, который жив.

Как устроена: на флешке один раздел ESP (FAT32), в нём копия загрузчика
Debian (`shim` + `grub`) по **запасному пути** `EFI/BOOT/BOOTX64.EFI`. Её
`grub.cfg` только находит зеркало по UUID и передаёт управление обычному
`/boot/grub/grub.cfg` - поэтому новые ядра подхватываются сами.

> Запасной путь `EFI/BOOT` обязателен. Реальный случай: в памяти UEFI не было
> ни одной записи (`sudo efibootmgr -v` -> `No BootOrder is set`), прошивка
> находит загрузчик только по этому пути.

**Перенос на новую флешку с рабочей.** Обе вставлены. Опознать по серийнику:

```
lsblk -o NAME,SIZE,TYPE,FSTYPE,LABEL,PARTLABEL,MOUNTPOINT,MODEL,SERIAL,TRAN
```

Смонтировать старую (по метке её раздела) только на чтение:

```
sudo mkdir -p /mnt/oldusb /mnt/newusb
```

```
sudo mount -o ro /dev/disk/by-label/МЕТКА_СТАРОЙ /mnt/oldusb
```

```
sudo find /mnt/oldusb -type f -exec ls -la {} +
```

**ОЖИДАЕТСЯ:** `EFI/BOOT/` с `BOOTX64.EFI`, `BOOTX64.CSV`, `grub.cfg`,
`grubx64.efi`, `mmx64.efi`.

⛔ **СТОП.** Дальше новая флешка стирается. Убедись, что `sdX` - это она:

```
lsblk -no SERIAL,SIZE /dev/sdX
```

Новая флешка не должна быть смонтирована (`sudo umount` её разделов, иначе
`wipefs` ответит "Устройство или ресурс занято"):

```
sudo wipefs -a /dev/sdX1
```

```
sudo wipefs -a /dev/sdX
```

```
sudo parted -s /dev/sdX mklabel gpt mkpart ESP fat32 1MiB 513MiB set 1 esp on
```

Метка - **другая**, чем у старой, иначе `by-label` их перепутает:

```
sudo mkfs.vfat -F 32 -n НОВАЯ_МЕТКА /dev/sdX1
```

```
sudo mount /dev/disk/by-label/НОВАЯ_МЕТКА /mnt/newusb
```

```
sudo cp -r /mnt/oldusb/EFI /mnt/newusb/
```

```
sudo diff -r /mnt/oldusb/EFI /mnt/newusb/EFI && echo COPY-OK
```

```
sudo umount /mnt/newusb /mnt/oldusb
```

**Проверка - только у монитора:** выключить, вынуть старую флешку, при
включении F8 (меню загрузки ASUS), выбрать новую. Загрузилась -> в BIOS
поставить её первой в порядке загрузки.

> Две флешки сразу могут сбить порядок: прошивка ставит первой не ту и,
> не найдя на ней загрузчика, уходит на SATA. Лишнюю - вынуть.
>
> После обновления `grub` через `apt` копия на флешке **сама не
> обновляется** - повтори перенос с системного ESP (`/boot/efi/EFI/debian/`
> -> `EFI/BOOT/` на флешке, `shimx64.efi` переименовать в `BOOTX64.EFI`).

## Шпаргалка

| Задача | Команда |
|---|---|
| какие диски есть | `lsblk -o NAME,SIZE,MODEL,SERIAL,FSTYPE,LABEL,MOUNTPOINT` |
| постоянные имена | `ls -l /dev/disk/by-id/ \| grep ata- \| grep -v part` |
| здоровье диска | `sudo smartctl -a /dev/disk/by-id/ata-...` |
| длинный тест / результат | `sudo smartctl -t long ...` / `sudo smartctl -l selftest ...` |
| где фото Immich на самом деле | `sudo docker inspect immich_server --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}'` |
| свободное место | `df -h /mnt/*` |
| бэкап сейчас | `sudo /usr/local/sbin/backup-immich.sh --force` |
| журнал бэкапа | `tail -20 /var/log/backup-immich.log` |
| спит ли диск | `sudo hdparm -C /dev/disk/by-id/ata-...` |

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| после перезагрузки фото не открываются, `ENOENT` | Docker стартовал раньше диска | 8.4.1, затем `cd ~/immich && sudo docker compose down` и `up -d` |
| системный SSD внезапно заполнился | Immich писал в пустую точку монтирования | 8.4.1; найти: `sudo du -xsh /mnt/*` (с `-x` считается только системный диск) |
| шлюз после перезагрузки в аварийном режиме | в `fstab` строка без `nofail`, диска нет | вход с монитора, `nano /etc/fstab`, добавить `nofail` |
| SMART молчит про новый диск | его нет в `smartd.conf` или он указан буквой | 8.8, Часть 4 раздел 11 |
| бэкап пишет `!= SRC` | библиотеку перенесли, а `SRC` нет | поправить `SRC` (8.6 п.8) |
| бэкап всегда "тихие часы" | таймер срабатывает в часы `QUIET_*` | время таймера вне тихих часов или `QUIET_FROM=24; QUIET_TO=0` |
| шумный диск не засыпает | нет `-c ata` или его будит другой процесс | 8.9; `sudo iotop -o` покажет, кто читает |
