## РАЗДЕЛ 00 - СПЕРВА КЛИЕНТ И ПУТЬ ТРАФИКА

⚠️ **Реальный случай:** "тормозит весь шлюз". Часами проверяли nftables,
conntrack, MTU, WARP, DNS - шлюз был исправен. На ПК был **выключен**
проводной адаптер, и Windows гнала трафик через адаптер Tailscale с релеем
в другой стране.

**Правило:** пока не доказано, что трафик клиента идёт через шлюз нужным
адаптером на полной скорости, - не трогай шлюз.

### 00.1 - Какой адаптер работает (на клиенте, Windows)

```
ipconfig /all
```

Ищи:
- активный адаптер с адресом `192.168.50.x` и шлюзом `192.168.50.1`;
- второй живой адаптер: `Tailscale`, `WireGuard`, `TAP`, `AmneziaVPN`,
  `Hyper-V`, `VMware`, `VirtualBox`. Если у VPN-адаптера не
  `Media disconnected` - он перехватывает трафик, и тест шлюза
  бессмысленен.

```
netsh interface show interface
```

Нужный проводной адаптер обязан быть `Enabled` / `Connected`.

### 00.2 - Скорость линка

PowerShell на клиенте:

```
Get-NetAdapter | Select-Object Name, Status, LinkSpeed
```

`100 Mbps` там, где должен быть `1 Gbps` - кабель или порт, не шлюз.

### 00.3 - Клиент напрямую в шлюз

Если 00.1-00.2 чистые, а тормозит - подключи клиента кабелем **напрямую** в
LAN-порт шлюза (или в свитч рядом), минуя точки доступа.
- напрямую быстро -> виновато промежуточное оборудование;
- напрямую тоже плохо -> переходи к разделам ниже.

> Tailscale на клиенте вместе с другим VPN-клиентом - не утечка. Tailscale
> держит только диапазон `100.64.0.0/10`, остальной трафик идёт как обычно.

### 00.4 - Линк шлюз <-> терминал и оптика (сначала железо)

⚠️ **Реальный случай:** интернет у всего дома пропадал примерно на минуту и
возвращался сам. Подозревали туннели и VPS. Журнал ядра показал, что рвался
**физический линк** до PON-терминала, а причиной был плохо державшийся
оптический коннектор. Переткнули - всё прошло.

**Правило:** при обрывах "у всех сразу" первым делом - физика.

Падал ли линк `wan` (на **шлюзе**):

```
sudo journalctl -k --since "-7d" --no-pager | grep "wan: Link is" | tee /tmp/wanflaps.log
```

- пусто -> линк не падал, причина выше по пути (раздел 4, 12);
- пары `Link is Down` / `Link is Up` -> физика: кабель шлюз-терминал,
  порт терминала, сам терминал, оптика.

> Подсказка в той же строке: если после восстановления изменился
> `flow control` (например, `rx/tx` -> `off`), порт **на стороне терминала**
> переинициализировался - терминал перезагрузился или сбросил свой свитч.

Скорость и ошибки порта:

```
sudo ethtool wan | grep -E "Speed|Duplex|Link detected"
```

**ОЖИДАЕТСЯ:** `1000Mb/s`, `Full`, `yes`. `100Mb/s` - кабель или порт.

```
ip -s link show wan
```

Растущие `errors` - кабель или порт.

**В веб-интерфейсе PON-терминала** (статус):
- **время работы** - если оно совпадает со временем обрыва, терминал
  перезагружался (сам или его перезагрузил провайдер);
- **уровень приёма (Rx)** - норма для GPON примерно от -8 до -27 дБм.
  Обычные значения у абонента -18…-25: оптический сплиттер провайдера сам
  съедает ~17-21 дБ. Ближе к -28 и ниже - вызывать провайдера.

Оптика:
- коннектор SC должен защёлкиваться **со щелчком**; разболтанный - менять шнур;
- торцы не трогать пальцами, держать колпачки; пыль на торце съедает дБ;
- **APC (зелёный) и UPC (синий) напрямую не соединять** - только гибридным
  шнуром или гибридным переходником;
- ⛔ металлический переходник с надписью `5dB`/`10dB` - это **аттенюатор**
  (ослабляет сигнал). На обычной линии его не ставить.

## РАЗДЕЛ 1 - Сайт не открывается

### 1.1 - Резолвится ли домен

```
dig +short проблемный-сайт.com @127.0.0.1
```

Пусто -> раздел 6.

### 1.2 - Резолвит ли клиент через шлюз

```
sudo journalctl -u dnsmasq -f
```

Открой сайт на клиенте. Бегут строки `query[A] ...сайт...` -> хорошо, дальше.
**Тишина** -> клиент резолвит мимо шлюза -> раздел 2. Выход - Ctrl+C.

### 1.3 - В каком наборе IP

```
D=проблемный-сайт.com; for ip in $(dig +short $D @127.0.0.1 | grep -E '^[0-9.]+$'); do echo "== $ip"; for s in endpoints ru_cidr ru_direct cf_warp warp_force zapret_direct ai_direct voice_direct; do sudo nft get element ip gwroute $s "{ $ip }" >/dev/null 2>&1 && echo "  $s"; done; done
```

Расшифровка - Часть 3, раздел 1.

### 1.4 - Какой путь работает (три запроса)

```
curl -sS -o /dev/null -w "direct: %{http_code} %{time_total}s\n" --max-time 15 https://проблемный-сайт.com/
```

```
curl -sS -o /dev/null -w "warp: %{http_code} %{time_total}s\n" --max-time 15 --interface vpn-main https://проблемный-сайт.com/
```

```
curl -sS -o /dev/null -w "vps: %{http_code} %{time_total}s\n" --max-time 15 --interface vpn-amz https://проблемный-сайт.com/
```

- `000` - путь закрыт; любой код (даже `403`) - связь есть;
- `403` только через WARP - сайт блокирует адреса Cloudflare -> VPS.

Сравни с 1.3: сайт лежит в полосе, путь которой закрыт? Перенеси в рабочую
(Часть 3, раздел 2).

**Все полосы одной командой** (подставь адрес целиком, со схемой и портом):

```
U=https://проблемный-сайт.com; for i in wan vpn-main vpn-backup vpn-amz; do curl -skS -m 8 --interface $i -o /dev/null -w "$i: код %{http_code}, соединение %{time_connect}s, всего %{time_total}s\n" "$U" 2>/dev/null || echo "$i: нет ответа"; done
```

- `соединение` больше нуля, а код `000` -> TCP установлен, но сервер не
  ответил на HTTP. Чаще всего **не та схема**: на порту HTTPS, а запрос по
  `http://` (сервер ждёт TLS и молчит). Пример - панели хостинга на `:8888`.
  Повтори с `https://`;
- `-k` нужен для голых IP и самоподписанных сертификатов.

> Домен из набора `ru_direct`, а напрямую не работает, работает только
> WARP -> `06-warp-force.conf` (Часть 3, 2.1). Скрипт `gw-domain-move.sh ...
> warp` тут **не поможет**: он только снимает ручное назначение.

### 1.5 - ⛔ Ловушка: `ip route get` без `iif` врёт про клиентов

```
ip route get АДРЕС
```

показывает путь **самого шлюза**, почти всегда `dev wan`. Для клиента:

```
ip route get АДРЕС from 192.168.50.100 iif lan
```

Метка ставится в `prerouting`, поэтому для точного ответа добавь метку
набора: `... iif lan mark 0x100` (напрямую) или `mark 0x200` (VPS).

**Надёжнее всего - живой трафик.** Запусти и дождись `listening on any`:

```
sudo tcpdump -i any -n icmp and host АДРЕС
```

потом на клиенте `ping проблемный-сайт.com`. Видишь цепочку
`lan In -> vpn-main Out -> vpn-main In -> lan Out` - **шлюз исправен**,
проблема у клиента (раздел 00). Ctrl+C - выход.

### 1.6 - Сайт грузится частично (без стилей, картинок)

Две причины:

1. **Ресурсы с другого домена.** F12 -> "Сеть" -> запросы с ошибкой. Их
   домен (CDN) положи в ту же полосу, что и сайт.
2. **Общий IP Cloudflare.** Реальный случай: `.ru`-сайт за Cloudflare
   утащил общий IP в `ru_direct`, а Cloudflare напрямую режется - у
   соседнего сайта на том же IP пропали стили. Набор `cf_warp` возвращает
   все адреса Cloudflare в WARP. Проверь, что правила на месте:

```
sudo nft list chain ip gwroute gwmark | grep -cE '@cf_warp|@warp_force'
```

**ОЖИДАЕТСЯ:** `2`. Меньше - правила потерялись, `sudo systemctl restart gw-routing`
и затем `sudo systemctl start gw-feeder`.

### 1.7 - Ошибка сертификата

```
echo | openssl s_client -connect проблемный-сайт.com:443 -servername проблемный-сайт.com 2>/dev/null | openssl x509 -noout -issuer -subject -dates
```

- издатель российский (Ростелеком, "Минцифры" и т.п.) - подмена на пути,
  сайт должен идти через туннель;
- нормальный издатель, но браузер ругается - проверь время на клиенте и
  нет ли на нём антивируса с подменой HTTPS.

### 1.8 - Сайт работает "через раз"

- Домен в двух файлах с **разными** наборами:

```
grep -rn 'проблемный-сайт' /etc/dnsmasq.d/
```

Оставь одну строку.

- Сайт отдаёт много разных IP, часть попала в набор, часть нет (CDN с
  прыгающими адресами). Прогрей: `dig` несколько раз; если не помогает -
  такой сайт лучше оставить в WARP (дефолт), а не тащить в ручную полосу.

### 1.9 - Полоса правильная, а всё равно не работает

Ровно этот путь (1.4) закрыт с обеих сторон: не пускает WARP и режется
напрямую. Решение - VPS (`07-vps-manual.conf`).

### 1.10 - Сервер по IP:порт не отвечает ни через одну полосу

Нужен **текст ошибки**, а не только код (без `2>/dev/null`):

```
for i in wan vpn-main vpn-amz; do echo "== $i"; curl -skS -m 8 --interface $i -o /dev/null https://IP:ПОРТ/; done
```

| Ошибка | Время | Значит |
|---|---|---|
| `(7) Failed to connect ... Could not connect to server` | ~время пинга (30-60 мс) | сервер **сам отказал**: на порту ничего не слушает или файрвол отвечает отказом |
| `(28) Connection timed out` | весь таймаут | пакеты пропадают по дороге или на сервере `drop` |

Жив ли сам сервер:

```
ping -c 3 IP
```

**Кто прислал отказ - сервер или фильтр по дороге.** Сначала обнови sudo
(в фоне он не спросит пароль):

```
sudo -v
```

```
(sudo timeout 8 tcpdump -ni wan -v -c 6 host IP and tcp 2>&1 | tee /tmp/rst.log &); sleep 2; curl -skS -m 5 --interface wan -o /dev/null https://IP:ПОРТ/; sleep 6
```

Ищи ответ от `IP` с флагом `[R.]` и смотри его `ttl`:
- `ttl` такой же, как у пинга (и `id 0`) -> отказ прислал **сам сервер**.
  Шлюз и полосы ни при чём. Если сервер чужой - писать владельцу: "сервер
  пингуется, порт отвечает сбросом соединения с разных адресов";
- `ttl` заметно другой -> сброс подделан по дороге (фильтр провайдера),
  пробуй другую полосу.

> `cksum incorrect` на **своих** исходящих пакетах - норма: контрольную
> сумму считает сетевая карта уже после tcpdump.

### 1.11 - Сайт открывается, а видео тормозит (YouTube и т.п.)

Страница идёт через WARP, а видеопоток - **мимо него**. Видеосерверы часто
стоят кэшем внутри сети провайдера с российскими IP. Такие IP попадают в
`ru_cidr` и уходят напрямую, где видео режут. Десктоп-VPN на ПК при этом
"летает" - он заворачивает в туннель всё подряд.

**Что идёт напрямую прямо сейчас.** Включи видео на клиенте и сразу:

```
sudo timeout 20 tcpdump -nn -q -i wan '(tcp or udp) and port 443' 2>/dev/null | awk '{print $3; print $5}' | grep -v '^АДРЕС_WAN_ШЛЮЗА' | cut -d. -f1-4 | sort | uniq -c | sort -rn | head -10
```

На порт 443 через `wan` идёт только прямой трафик: WARP и VPS ходят на свои
порты. Адрес с тысячами пакетов - кандидат. Какое устройство его качает:

```
sudo conntrack -L -d АДРЕС 2>/dev/null | head -5
```

`src=` - IP клиента; по нему `grep IP /var/lib/misc/dnsmasq.leases`. Не тот
клиент - значит, это не твоё видео, а законный прямой трафик другого
устройства.

**Лечение** - домены сервиса в `warp_force` (он стоит после `ru_cidr` и
перебивает его). Реальный случай, YouTube:

```
echo 'nftset=/youtube.com/googlevideo.com/ytimg.com/ggpht.com/youtu.be/youtube-nocookie.com/youtubei.googleapis.com/4#ip#gwroute#warp_force' | sudo tee -a /etc/dnsmasq.d/06-warp-force.conf
```

```
sudo systemctl restart dnsmasq
```

На клиенте сбросить DNS (`ipconfig /flushdns` в PowerShell) и перезапустить
браузер. Проверка - в наборе появились адреса Google:

```
sudo nft list set ip gwroute warp_force
```

> `warp_force` значит "**не напрямую**", а не "только WARP": он снимает
> метку `0x100`, и трафик идёт полосой дома (таблица 100). При аварии WARP
> он вместе со всем домом временно уйдёт на VPS.
>
> Счётчик `nft list set ... | grep -c` ничего не значит: элементы набора
> печатаются в одну-две строки. Смотри сам вывод.

### 1.12 - Сайт режется по адресу сервера (TLS с адреса запрещён)

С конца октября 2026 ТСПУ умеет запрещать **любой** TLS с отдельных адресов,
не глядя на имя сайта (первыми попали группы серверов Google `74.125.x.x`).
Признак: напрямую не работает ничего, через туннель - работает.

Адрес проблемного сервера (из `dig` или из вкладки "Сеть" в браузере) - и
подключиться к нему, назвав **постороннее** имя:

```
for i in wan vpn-main; do printf '%-9s ' $i; curl -4s -o /dev/null -m 10 -w '%{http_code}\n' --interface $i --connect-to ::АДРЕС:443 https://example.com || echo "нет ответа"; done
```

| `wan` | `vpn-main` | Значит |
|---|---|---|
| нет ответа | любой код (даже `404`/`421`) | фильтр **по адресу**: имя ни при чём, стратегии обхода по имени бесполезны |
| код есть | код есть | адрес не запрещён, ищи причину в имени (1.3-1.4) |
| нет ответа | нет ответа | сервер лежит или режет чужие имена - проверь его настоящим именем |

**Лечение** - домены этого сервиса в туннель (`06-warp-force.conf`, как в
1.11). Туннель прячет и адрес, и TLS - фильтру нечего читать.

> Почему не обход вроде zapret: фильтр узнаёт TLS по первым трём байтам
> **ответа сервера** (`16 03 03`) и смотрит только в пределах TCP-окна.
> Единственный рабочий трюк - окно 2 байта (`wssize 1:1`) - режет скорость
> соединения в десятки раз до его конца (~1,6 Мбит/с при пинге 20 мс).
> Для Google фильтр к тому же ~10 минут помнит исход соединения. Разбор:
> [zapret.moe, ТСПУ режет TLS с адресов Google](https://wiki2.zapret.moe/DPI/tspu-tls-ip-filter-tcp-window-october-2026)
> (по сообщениям форума ntc.party, 23-31.10.2026).

## РАЗДЕЛ 2 - Российские сайты не работают на одном устройстве

Типичная картина: на ПК всё хорошо, на телефоне `ozon`, `gosuslugi` и т.п.
не открываются или пишут "отключите VPN".

Причина почти всегда одна: **устройство резолвит DNS само**, мимо шлюза.
Российские домены не попадают в `ru_direct` и уходят в WARP.

Проверь по очереди **на устройстве**:

1. **Android:** Настройки -> Сеть -> "Частный DNS" -> **"Автоматически"** или
   **"Отключено"**. Если там конкретное имя (`dns.adguard.com` и т.п.) - при
   закрытом порте 853 (Часть 1) интернет у устройства пропадёт совсем.
2. **Браузер:** "Безопасный DNS" / "Secure DNS" / "DNS через HTTPS" ->
   **выкл**. Chrome, Opera, Яндекс: Настройки -> Конфиденциальность ->
   Безопасность. Firefox: Настройки -> Приватность -> DNS через HTTPS.
3. **Свой VPN на устройстве** (приложение) - выключить.

Проверка: `sudo journalctl -u dnsmasq -f` на шлюзе, на устройстве открыть
сайт - должны побежать запросы с его IP.

Найти IP устройства по аренде DHCP:

```
cat /var/lib/misc/dnsmasq.leases
```

> С 15.04.2026 многие российские сервисы и приложения отказывают при
> включённом VPN. Приложения видят VPN **на самом устройстве**, а сайты -
> только IP. На шлюзе VPN не виден устройству, но российские адреса обязаны
> идти напрямую, иначе сервис видит иностранный IP.

## РАЗДЕЛ 3 - Шлюз ходит, клиенты нет (masquerade)

**Симптом:** `curl --interface vpn-xxx` с шлюза работает, у клиента через ту
же полосу - таймаут.

**Причина:** нет masquerade на этом интерфейсе. Пакеты клиента уходят в
туннель с адресом `192.168.50.x`, ответ не возвращается.

```
sudo tcpdump -i lan -n host IP_КЛИЕНТА and port 443
```

Есть исходящие SYN, нет ответных SYN-ACK - это оно. Ctrl+C.

```
sudo nft list chain ip gwroute nat
```

**ОЖИДАЕТСЯ:** строка `oifname "ИМЯ" masquerade` для **каждого** туннеля.
Нет - добавь в `/etc/gwroute.nft` (цепочка `nat`) и:

```
sudo systemctl restart gw-routing
```

```
sudo systemctl start gw-feeder
```

> Правило: **новый туннель = сразу masquerade** для него.

## РАЗДЕЛ 4 - Нет интернета у всего дома

### 4.1 - Куда смотрит таблица 100

```
ip route show table 100
```

| Первая строка | Значит | Дальше |
|---|---|---|
| `default dev vpn-main` | дефолт в порядке | 4.5 |
| `default dev vpn-backup` | WARP лёг, работает запасной | 4.3 |
| `blackhole default` (без metric) | kill-switch: все слоты мертвы | 4.2 |
| только `blackhole ... metric 1000` | оркестратор не ставит маршрут | 4.4 |

### 4.2 - Kill-switch: почему все слоты мертвы

```
sudo awg show vpn-main latest-handshakes
```

Второе число - время рукопожатия (секунды с 1970); `0` - рукопожатия нет.

```
journalctl -t gw-orchestrator -n 20 --no-pager
```

```
journalctl -t warp-pick -n 30 --no-pager
```

- **WAN жив?** `ping -c2 -I wan 1.1.1.1`. Нет - проблема у провайдера или
  кабеля.
- **WARP мёртв** -> `sudo /usr/local/sbin/warp-pick.sh --force`. Все конфиги
  пула мимо -> пул протух, Часть 5.
- **Туннель жив (`curl --interface vpn-main` работает), а kill-switch держится**
  -> 4.4.

### 4.3 - Застряли на `vpn-backup`

Оркестратор возвращает `vpn-main` сразу, как только у него свежее
рукопожатие, а если WARP мёртв - сам запускает перебор конфигов (не чаще раза
в 15 минут, Часть 2, Шаг 2.11). Сначала журнал:

```
sudo journalctl -t gw-orchestrator -t warp-pick --since "-2h" --no-pager | tail -40
```

- **Нет строк `WARP мёртв ... запускаю перебор`**, хотя дом на `vpn-backup`
  дольше 15 минут -> в оркестраторе нет блока авто-перебора или нет
  `warp-rotate.service` (Шаг 2.12.1). Реальный случай: до этого блока дом два
  часа сидел на VPS, пока не сработал таймер ротации;
- **Перебор идёт, но `все попытки мимо`** -> пул протух, Часть 5;
- **`ВЫБРАН: ...`, а дом всё равно на `vpn-backup`** - рукопожатие "старое":

```
sudo grep -i keepalive /etc/gateway/tunnels/vpn-main.conf
```

**ОЖИДАЕТСЯ:** `PersistentKeepalive = 25`. Нет - без трафика рукопожатие не
обновляется, и оркестратор не видит WARP живым. Лечение:

```
sudo /usr/local/sbin/warp-pick.sh --force
```

(его `prep` вписывает keepalive).

### 4.4 - Туннель жив, а дом в blackhole или маршрута нет

1. **Имена каскада:**

```
sudo bash -c 'source /etc/gateway/gateway.conf; for s in $VPN_CASCADE_ORDER; do ip link show $s >/dev/null 2>&1 && echo "$s: есть" || echo "$s: ИНТЕРФЕЙСА НЕТ"; done'
```

Любое "ИНТЕРФЕЙСА НЕТ" - поправь `VPN_CASCADE_ORDER` в
`/etc/gateway/gateway.conf` (реальный случай: там было старое `vpn-WARP`).

2. **Таймер оркестратора:**

```
systemctl is-active gw-orchestrator.timer
```

`inactive` -> `sudo systemctl enable --now gw-orchestrator.timer`.

3. **warp-pick завис и держит lock** (оркестратор молчит, в журнале
   "warp-pick активен, тик пропущен"):

```
pgrep -a warp-pick
```

Висит дольше 5 минут - `sudo pkill -f warp-pick.sh`, потом
`sudo systemctl start gw-orchestrator`.

### 4.5 - Таблица в порядке, а интернета нет

```
ip rule
```

Должны быть правила 8800, 8810, 8900, 8996, 9500 (Часть 2, Шаг 2.10.2). Нет
- `sudo systemctl restart gw-routing`, затем `sudo systemctl start gw-feeder`.

```
sudo nft list tables
```

Должны быть `inet gw_fw`, `ip gw_nat`, `ip gw_dnsredirect`, `ip gwroute`.

Дальше - DNS (раздел 6) и masquerade (раздел 3).

```

```


адрес, файл `/etc/dnsmasq.d/09-tmp-override.conf`:

```
address=/проблемный-сайт.com/НОВЫЙ_IP
```

`sudo dnsmasq --test`, `sudo systemctl restart dnsmasq`. **Убери файл**, когда
кэш обновится (проверяй `dig @127.0.0.1` без файла), иначе забудешь, и при
следующем переезде сайт сломается.

## РАЗДЕЛ 7 - После перезагрузки что-то не встало

```
tail -45 /var/log/bootcheck.log
```

```
systemctl --failed
```

Упавший юнит -> `journalctl -u ИМЯ -n 30 --no-pager`.

Все предупреждения текущей загрузки:

```
sudo journalctl -b -p warning --no-pager | tee /tmp/boot-warn.log | tail -40
```

Живы ли все туннели (норма - каждый моложе 180 с):

```
sudo awg show all latest-handshakes | while read i k t; do echo "$i: $(( $(date +%s) - t )) с назад"; done
```

Слота нет в списке -> `systemctl status vpn-slot@ИМЯ --no-pager`.

Частое:
- **`vpn-slot@...` в `failed`, а в журнале `awg-quick` отработал до конца**
  (адрес, mtu, маршрут) -> упал пост-скрипт `vpn-slot-up.sh`. Проверь
  `tail -1 /usr/local/sbin/vpn-slot-up.sh` - должно быть `exit 0` (Часть 2,
  Шаг 2.5). После исправления: `sudo systemctl restart vpn-slot@ИМЯ`;
- **`martian source 192.168.50.x ... on dev wan`** сразу после загрузки ->
  клиенты первые минуты выходили без NAT. Проверь
  `sudo nft list table ip gw_nat`: там должно быть `oifname "wan"`, а не
  `"$WAN"` (Часть 1, Шаг 1.7.3);
- **`Unknown device type` / `Falling back to slow userspace`** - модуля ядра
  AmneziaWG нет, туннели на `amneziawg-go`. Работает, но слоты поднимать
  только через systemd (Часть 2, Шаг 2.1);
- **слот не поднялся** -> `sudo systemctl restart vpn-slot@vpn-main`;
  ошибка `IPv6 is disabled` или `resolvconf: command not found` - в конфиге
  IPv6-адрес или строка `DNS=` (Часть 2, Шаг 2.5);
- **`Module amneziawg not found`** после обновления ядра -> Часть 2, Шаг 2.1;
- **российские сайты в WARP первые 5 минут** - `ru_cidr` пуст до первого
  прогона фидера, это нормально; дольше -> `sudo systemctl start gw-feeder`;
- **после долгого простоя нет интернета** - `warp-pick` ждёт WAN до 120 с,
  проверь `journalctl -t warp-pick -n 20 --no-pager` и раздел 4;
- **WAN получил другой адрес** (`WAN-IP <<<<` в отчёте) - закрепи адрес в DHCP
  PON-терминала (Часть 2, Шаг 2.15);
- **`warp-pick-boot.service` в `failed`, в журнале `другой warp-pick уже
  работает`** -> оркестратор запустил перебор в первые минуты после загрузки
  и перехватил блокировку. Интернет при этом есть, но в оркестраторе нет
  задержки 10 минут (`/proc/uptime ... -ge 600`, Часть 2, Шаг 2.11). После
  правки: `sudo systemctl reset-failed warp-pick-boot.service`;
- **`Restart=on-failure` у слота не срабатывает** - на модуле ядра WARP
  поднимает `warp-pick` в обход юнита (`vpn-slot@vpn-main` = `inactive`).
  Это нормально: страхует авто-перебор оркестратора.

## РАЗДЕЛ 8 - Пропал удалённый доступ (Tailscale)

```
tailscale status | head -3
```

- свой узел `offline` при живом интернете - не доходит до координационного
  сервера Tailscale. Сравни:

```
curl -s -o /dev/null -w "%{http_code}\n" --max-time 10 https://controlplane.tailscale.com/health
```

```
curl -s -o /dev/null -w "%{http_code}\n" --max-time 10 --interface vpn-main https://controlplane.tailscale.com/health
```

`000` напрямую и код через WARP - сервер режется на прямом канале. На старой
прямой схеме это лечили маршрутом подсети сервера через туннель для трафика
самого шлюза. В инверсной схеме случай не воспроизводился, проверенного
фикса под неё нет - разбирай отдельно, не правь `gwroute.nft` наугад.

- службы на Tailscale-адресе (панель) не стартуют после загрузки -> нет
  drop-in с `Restart=always` (Часть 3, 5.1).

**Узел не `offline`, но не отвечает** (`tailscale status` на ПК: `active;
relay "...", tx 2808 rx 0`, `tailscale ping` - `timed out`). Сервер Tailscale
считает узел живым, но ответы от него не идут. С другой машины в той же сети
терминала (второй шлюз) проверь обычную связь:

```
ping -c 3 WAN_АДРЕС_ПРОБЛЕМНОГО_ШЛЮЗА
```

`Destination Host Unreachable` **от своего же адреса** - на этом адресе в сети
вообще никого: нет линка (кабель, порт, сетевая карта) или шлюз получил
другой адрес (смотри список клиентов в веб-панели терминала по MAC).
Реальный случай: помогла перезагрузка шлюза. Если повторяется - смотри
журнал прошлой загрузки: `sudo journalctl -b -1 -k | grep -iE 'link|r816|e1000'`.

**Запасной путь без Tailscale:** SSH из LAN (`user@192.168.50.1`) или через
туннель своего VPS (Часть 6).

## РАЗДЕЛ 10 - Подозрительное устройство в сети

Признаки: в журнале dnsmasq от одного IP - запросы к странным доменам
(случайные буквы, `.xyz`, `.shop`, `.site`), устройство стучится к шлюзу на
нестандартные порты.

1. Что спрашивает устройство (⛔ IP подставь его):

```
sudo journalctl -u dnsmasq --since "1 hour ago" | grep 'from ПОДСТАВЬ_IP$' | grep -oE 'query\[[A-Z]+\] [^ ]+' | awk '{print $2}' | sort | uniq -c | sort -rn | head -40 | tee /tmp/device-domains.txt
```

2. Мусорные домены - в `08-block.conf`, устройство - в изоляцию от шлюза
   (Часть 1, раздел "Защита шлюза от устройств в LAN").
3. Android-устройство - проверь ADB (там же).
4. Не открыты ли службы шлюза для всей LAN:
   `sudo ss -tlnp | grep -v 127.0.0.1`.

Лог попыток устройства (живёт до перезагрузки), ⛔ MAC подставь:

```
sudo nft add table inet devlog
```

```
sudo nft add chain inet devlog fwd '{ type filter hook forward priority -10; }'
```

```
sudo nft add rule inet devlog fwd ether saddr ПОДСТАВЬ_MAC ct state new log prefix '"DEVLOG "'
```

Смотреть: `sudo journalctl -k | grep DEVLOG | tail -50`. Убрать:
`sudo nft delete table inet devlog`. ⚠️ Имя цепочки `forward` занято
ключевым словом - отсюда `fwd`.

## РАЗДЕЛ 11 - Диски и мониторинг SMART

⚠️ **Реальный случай:** добавили диск - буквы `sda/sdb/...` сдвинулись.
`smartd` следил по `/dev/sdb` и молча переключился на другой диск, а три
диска остались без мониторинга. `hd-idle` тоже был настроен по букве.

**Правило:** в `smartd.conf`, `hd-idle` и любых скриптах диски указывать
по **`/dev/disk/by-id/...`** (модель + серийник), никогда по букве.
В `fstab` - по `UUID`.

Постоянные имена дисков:

```
ls -l /dev/disk/by-id/ | grep ata- | grep -v part
```

Нового диска сначала проверить здоровье (`sdX` - буква из `lsblk`):

```
sudo smartctl -a /dev/sdX | tee /tmp/smart-new.log
```

Смотреть: `Reallocated_Sector_Ct`, `Current_Pending_Sector`,
`Offline_Uncorrectable` (должны быть `0`), `Power_On_Hours`, ошибки в журнале.
Затем длинный тест поверхности (ничего не стирает, идёт часами в фоне):

```
sudo smartctl -t long /dev/sdX
```

Результат после окончания:

```
sudo smartctl -l selftest /dev/sdX
```

Строка `smartd.conf` на каждый диск (пример, ⛔ подставь свой by-id):

```
/dev/disk/by-id/ata-ПОДСТАВЬ_МОДЕЛЬ_СЕРИЙНИК -a -o on -S on -s (S/../../7/02|L/../../1/03) -W 5,50,55 -n standby,q -m <nomailer> -M exec /usr/local/sbin/smart-alert.sh
```

Для SSD длинный тест не нужен (`-s (S/../../7/02)`), пороги температуры
выше (`-W 5,60,70`), `-n standby,q` не нужен.

```
sudo systemctl restart smartd
```

```
sudo journalctl -u smartmontools -b --no-pager | tail -15
```

**ОЖИДАЕТСЯ:** строки `state written to ...` для каждого диска. Служба в
Debian называется `smartmontools` (`smartd` - её псевдоним), поэтому
`journalctl -u smartd` бывает пустым.

## РАЗДЕЛ 12 - netwatch: самописец обрывов

Когда обрывы короткие и "непонятно когда", ставим самописец. Раз в 10 с он
проверяет каждый путь отдельно и пишет в лог **только изменения** состояния.
При новом сбое дописывает снимок: рукопожатия, таблица 100, адрес `wan`.
Проверки привязаны к интерфейсам, поэтому инверсная схема (дом через WARP)
их не обманывает.

⛔ Подставь `ПОДСТАВЬ_IP_VPS` (публичный адрес своего VPS, Часть 6). Нет
своего VPS - удали три строки `vps_*`.

```
sudo tee /usr/local/sbin/netwatch.sh > /dev/null <<'EOF'
#!/bin/bash
# netwatch.sh - раз в 10 с проверяет пути шлюза, в лог пишет только смену
# состояния (OK <-> FAIL). При новом FAIL - снимок туннелей и таблицы 100.
LOG=/var/log/netwatch.log
VPS_IP=ПОДСТАВЬ_IP_VPS
declare -A last
stamp(){ date '+%F %T'; }
check(){  # имя, команда...
    local name="$1"; shift
    local st=FAIL
    "$@" >/dev/null 2>&1 && st=OK
    if [ "${last[$name]:-}" != "$st" ]; then
        echo "$(stamp) $name $st" >> "$LOG"
        if [ "$st" = FAIL ] && [ -n "${last[$name]:-}" ]; then
            {
                echo "  --- снимок $(stamp) ---"
                awg show all latest-handshakes | awk -v n="$(date +%s)" '{print "  "$1" рукопожатие "($3==0?"нет":n-$3" с назад")}'
                ip route show table 100 | sed 's/^/  t100: /'
                ip -br addr show wan | sed 's/^/  /'
            } >> "$LOG" 2>&1
        fi
        last[$name]=$st
    fi
}
dns_ok(){ [ -n "$(dig +time=2 +tries=1 @127.0.0.1 example.com +short 2>/dev/null)" ]; }
echo "$(stamp) netwatch старт" >> "$LOG"
while true; do
    PONGW=$(ip route show default dev wan 2>/dev/null | awk '{print $3; exit}')
    check pon      ping -c1 -W2 -I wan "${PONGW:-192.168.0.1}"
    check wan      ping -c1 -W2 -I wan 1.1.1.1
    check warp     ping -c1 -W2 -I vpn-main 1.1.1.1
    check vps_dir  ping -c1 -W2 -I wan "$VPS_IP"
    check vps_tun  ping -c1 -W2 10.78.0.1
    check vps_inet curl -s -m5 -o /dev/null --interface vpn-backup http://1.1.1.1
    check dns      dns_ok
    sleep 10
done
EOF
```

## Уроки (симптом -> причина -> решение)

| Симптом | Причина | Решение |
|---|---|---|
| сайт без стилей | `.ru`-сайт за Cloudflare утащил общий IP в `ru_direct` | набор `cf_warp` |
| сайт не пускает WARP и режется напрямую | блокировка с двух сторон | `07-vps-manual` |
| ручной домен утащил чужой сайт | один IP Cloudflare на двоих | не разводится, все сайты на IP в одной полосе |
| `.ru`-домен нужен через WARP | зона `.ru` шлёт напрямую | `06-warp-force` |
| РФ-сайты не работают на одном телефоне | Secure DNS в браузере / Частный DNS | выключить на устройстве |
| сервис Docker на шлюзе не открывается из LAN | трафик к Docker уходил в таблицу 100 | правило 8810 |
| застряли на запасном слоте | нет `PersistentKeepalive` | keepalive в `warp-pick` |
| весь дом в kill-switch при живом туннеле | имя в `VPN_CASCADE_ORDER` не совпадает | поправить `gateway.conf` |
| активировал конфиг - умер весь шлюз | нет `Table = off` | `gw-warp-activate` дописывает сам |
| поправил nftset, ничего не изменилось | `reload` вместо `restart` | `systemctl restart dnsmasq` |
| сайт переехал, шлюз отдаёт старый IP | кэш DNS (dnscrypt + AdGuard) | ждать или временный `address=` |
| проверка "напрямую" через 2ip.ru показывает WARP | сайт хостится вне РФ | проверять по `ip.mail.ru` |
| команда с `www.` сломалась | чат превратил домен в ссылку | домен без `www.` |
| строки в файле задвоились | повторный `sed -i '...a\'` | после вставки всегда `grep -n` |
| интернет у всех пропадает на минуту | плохо державшийся оптический коннектор | раздел 00.4: сначала железо |
| после перезагрузки туннели в `failed` | `vpn-slot-up.sh` без `exit 0` | Часть 2, Шаг 2.5 |
| `vpn-main` исчезает через ~40 с после выбора | `awg-quick` вне systemd при `amneziawg-go` | `restart_slot` через `systemctl` |
| ротация WARP никогда не срабатывает | двойной `flock` в `warp-rotate.service` | Часть 2, Шаг 2.12.1 |
| первые минуты после загрузки сайты не грузятся, `martian source` | `\$WAN` в `gw-nat.sh` | Часть 1, Шаг 1.7.3 |
| SMART "молчит" про диски после добавления нового | `smartd.conf` по букве `/dev/sdX` | раздел 11: by-id |
| `curl` к панели на порту: соединение есть, ответа нет | порт HTTPS, а запрос по `http://` | раздел 1.4: `https://` |
| `sudo` в фоновой команде: `не удаётся прочитать пароль` | sudo не может спросить пароль в фоне | сначала `sudo -v` |
| YouTube тормозит, а через десктоп-VPN летает | видеосерверы с российскими IP уходят напрямую через `ru_cidr` | раздел 1.11: домены в `warp_force` |
| дом часами на VPS после смерти WARP-конфига | оркестратор менял полосу, но WARP никто не чинил до таймера ротации | авто-перебор в оркестраторе (Часть 2, 2.11) |
| `warp-pick-boot` красный после загрузки | авто-перебор оркестратора перехватил блокировку при старте | задержка 10 мин (Часть 2, 2.11) |
| `journalctl -t X -u Y` пишет `No entries` | разные фильтры дают пересечение | две отдельные команды |
| шумный диск просыпается каждый день в одно время | ежедневная проверка даты бэкапа читала сам диск | Часть 8, 8.9.1: метка на SSD |
| `tailscale ping` молчит, узел не `offline` | у шлюза нет линка в сети терминала | раздел 8: `ping` с соседа, железо |
| сайт напрямую мёртв при любой стратегии, через VPN жив | ТСПУ запрещает TLS с адреса сервера, имя не важно | 1.12: проверка с посторонним именем, домены в туннель |
| медиа в Telegram грузится плохо, звонки рвутся | `voice_direct` пуст: фидер не скачал списки (DNS не работал при запуске), а WARP не пускает к DC2 Telegram `149.154.167.x` | `sudo systemctl start gw-feeder`; фидер с повторами и кэшем (`tools/patch-feeder.py`) |
| после перезагрузки РФ-сайты "иностранные", набор `ru_cidr` пуст | фидер молча не скачал подсети | то же: повторы + кэш в `/var/lib/gw-feeder` |
