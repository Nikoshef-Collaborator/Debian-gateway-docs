# ЧАСТЬ 1 - Фундамент шлюза с нуля

> **Сценарий:** новое железо, чистый диск. Ставим Debian, закрепляем имена
> сетевых карт, поднимаем сеть, firewall, NAT, DHCP и шифрованный DNS.
> Туннели и полосы - в Части 2.
>
> **Правила для ИИ-помощника - в Части 0. Они обязательны.** Коротко: одна
> команда за раз, сверка с "ОЖИДАЕТСЯ", на ⛔ СТОП - стоп, секреты не в чат.
>
> Все команды этой части выполняются **на шлюзе**.

---

## Что нужно из железа

- x86-компьютер для круглосуточной работы, 2-4 ГБ ОЗУ, SSD от 32 ГБ.
  Подходят списанные офисные ПК.
- **Две сетевые карты обязательны:** одна в интернет (**WAN**), вторая в дом
  (**LAN**). Для LAN лучше Intel (надёжные драйверы), WAN может быть любой.
- Клиенты подключаются к LAN через свитч или Wi-Fi-точку **в режиме точки
  доступа** (без своего DHCP и без двойного NAT).
- На время установки - монитор и клавиатура. Первые шаги могут оборвать SSH.

## Шаг 1.1 - Установить Debian 13

С USB-установщика Debian 13 (образ netinst):
- **сними** "GNOME / Desktop environment";
- **оставь** "SSH server" и "standard system utilities";
- разметка - ext4 на весь системный SSD;
- диски с данными, если есть, **не трогай**.

Пользователь, которого создашь при установке, дальше называется `user`.

**ПРОВЕРКА:** система загрузилась, видно приглашение вида `user@...:~$`.

## Шаг 1.2 - Определить сетевые карты

**Цель:** точно понять, какая карта WAN, какая LAN.

Воткни кабель интернета (от PON-терминала или роутера провайдера) **только в
одну** карту. Кабель в дом пока не подключай. Команда:

```
ip -br link
```

**ОЖИДАЕТСЯ:** список интерфейсов, например:

```
lo               UNKNOWN  00:00:00:00:00:00
enp5s0           UP       aa:bb:cc:dd:ee:01
enp1s0           DOWN     aa:bb:cc:dd:ee:02
```

- Карта со статусом `UP` - это **WAN**.
- Карта со статусом `DOWN` - это **LAN**.

Запиши себе **текущее имя** и **MAC** (третий столбец) каждой карты.

⛔ **СТОП:** не иди дальше, пока точно не знаешь, где WAN и где LAN.

**ЕСЛИ обе карты `DOWN`** -> кабель не воткнут или мёртвый. Воткни рабочий
кабель интернета в одну карту и повтори команду.

## Шаг 1.3 - Обновить систему и поставить пакеты

Пока сеть работает по-старому (через установщик Debian), ставим всё нужное.

Команда первая:

```
sudo apt update && sudo apt full-upgrade -y
```

**ОЖИДАЕТСЯ:** обновление прошло, в конце нет строк, начинающихся с `E:`.

**ЕСЛИ ошибка сети** -> проверь `ping -c2 1.1.1.1`. Пока ping не проходит,
дальше нельзя: кабель не в той карте (Шаг 1.2).

Команда вторая:

```
sudo apt install -y nftables dnsmasq network-manager curl wget git iproute2 tcpdump jq conntrack fail2ban python3-systemd unattended-upgrades bind9-dnsutils
```

**ОЖИДАЕТСЯ:** пакеты установились, нет строк с `E:`.

> Зачем (менять не нужно):
> - `dnscrypt-proxy` в списке нет специально: в Debian он старый, ставим
>   вручную на Шаге 1.9;
> - `bind9-dnsutils` даёт `dig`, на нём все проверки DNS;
> - `network-manager` будет управлять ТОЛЬКО картой WAN;
> - `nftables` нужен ради программы `nft`, сам сервис `nftables.service` НЕ
>   включаем;
> - `conntrack` нужен оркестратору (сбрасывает соединения при смене выхода);
> - `python3-systemd` нужен fail2ban.

## Шаг 1.4 - Закрепить имена карт `wan` и `lan` по MAC

**Почему это обязательно.** Имя вида `enp1s0` зависит от слота PCI. Перенёс
карту в другой слот (чистка от пыли, новый контроллер) - после перезагрузки
она называется `enp2s0`, и разом слепнут DHCP, DNS, firewall и NAT: они все
ждут старое имя. Реальный случай: кабели на месте, лампочки горят, а в доме
нет сети. Привязка к MAC убирает эту проблему, а заодно все скрипты дальше
пишутся под понятные имена `wan` и `lan`.

Команда первая - файл для WAN. ⛔ Вместо `ПОДСТАВЬ_MAC_WAN` впиши MAC WAN-карты
из Шага 1.2 (точно, с двоеточиями):

```
sudo tee /etc/systemd/network/10-wan.link > /dev/null <<'EOF'
[Match]
MACAddress=ПОДСТАВЬ_MAC_WAN

[Link]
Name=wan
EOF
```

**ОЖИДАЕТСЯ:** молча отработало.

Команда вторая - файл для LAN. ⛔ Вместо `ПОДСТАВЬ_MAC_LAN` впиши MAC LAN-карты:

```
sudo tee /etc/systemd/network/10-lan.link > /dev/null <<'EOF'
[Match]
MACAddress=ПОДСТАВЬ_MAC_LAN

[Link]
Name=lan
EOF
```

**ОЖИДАЕТСЯ:** молча отработало.

**ПРОВЕРКА:**

```
cat /etc/systemd/network/10-wan.link /etc/systemd/network/10-lan.link
```

**ОЖИДАЕТСЯ:** два блока, в каждом свой MAC и `Name=wan` / `Name=lan`.
Сравни MAC с записанными на Шаге 1.2 посимвольно.

Команда третья - обновить initramfs (переименование должно сработать уже на
ранней стадии загрузки):

```
sudo update-initramfs -u
```

**ОЖИДАЕТСЯ:** строка `update-initramfs: Generating /boot/initrd.img-...`.

> `.link`-файлы применяет **udev**, а не служба `systemd-networkd`. Сама
> `systemd-networkd` у нас выключена и не используется (см. "Чего на шлюзе
> быть не должно"). Новые имена появятся после перезагрузки на Шаге 1.6.

## Шаг 1.5 - Сеть: WAN под NetworkManager, LAN без менеджера

**Что делаем.** Установщик Debian настроил сеть через старую систему
`ifupdown` (`/etc/network/interfaces`). WAN переносим под NetworkManager. LAN
не отдаём никакому менеджеру: адрес на нём будет вешать маленький свой
скрипт. Так ни один менеджер не сможет случайно снять адрес шлюза.

### 1.5.1 - Запретить NetworkManager трогать LAN (ДО его включения)

```
sudo mkdir -p /etc/NetworkManager/conf.d
```

```
sudo tee /etc/NetworkManager/conf.d/unmanage-lan.conf > /dev/null <<'EOF'
[keyfile]
unmanaged-devices=interface-name:lan
EOF
```

**ОЖИДАЕТСЯ:** обе команды молча отработали.

### 1.5.2 - Убрать сетевые карты из ifupdown

⛔ Вместо `ПОДСТАВЬ_СТАРОЕ_ИМЯ_WAN` впиши текущее имя WAN-карты из Шага 1.2
(например `enp5s0`):

```
sudo sed -i -E 's/^([[:space:]]*(auto|allow-hotplug|iface)[[:space:]]+ПОДСТАВЬ_СТАРОЕ_ИМЯ_WAN.*)$/#\1/' /etc/network/interfaces
```

**ПРОВЕРКА:**

```
grep -E "auto|iface|allow-hotplug" /etc/network/interfaces
```

**ОЖИДАЕТСЯ:** без `#` в начале остались только строки про `lo`.

**ЕСЛИ есть живая строка про сетевую карту** -> открой
`sudo nano /etc/network/interfaces` и поставь `#` в начало каждой такой
строки. Живыми оставь только строки про `lo`.

### 1.5.3 - Включить NetworkManager

```
sudo systemctl enable NetworkManager
```

**ОЖИДАЕТСЯ:** может напечатать `Created symlink...` - это нормально.

> Запускать сейчас не нужно - он стартует после перезагрузки на Шаге 1.6 и
> сам создаст для карты `wan` профиль `Wired connection 1` с DHCP.

### 1.5.4 - Скрипт и юнит для адреса LAN

Если хочешь другую подсеть (не `192.168.50.0/24`), меняй её одинаково во ВСЕХ
частях документации. Проще оставить эту.

```
sudo tee /usr/local/sbin/gw-lan.sh > /dev/null <<'EOF'
#!/bin/bash
# Статический IP на LAN-карте шлюза. Маршрутизацию не трогает.
LAN=lan
ip addr replace 192.168.50.1/24 dev "$LAN"
ip link set "$LAN" up
EOF
```

```
sudo chmod 755 /usr/local/sbin/gw-lan.sh
```

```
sudo tee /etc/systemd/system/gw-lan.service > /dev/null <<'EOF'
[Unit]
Description=Static IP on LAN interface (gateway)
After=network-pre.target
Before=dnsmasq.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/gw-lan.sh

[Install]
WantedBy=multi-user.target
EOF
```

```
sudo systemctl daemon-reload
```

```
sudo systemctl enable gw-lan
```

**ОЖИДАЕТСЯ:** все команды молча отработали (последняя может напечатать
`Created symlink...`).

⛔ **СТОП про SSH.** Следующий шаг - перезагрузка, после которой карты
получат новые имена, а сетью начнёт управлять NetworkManager. Если что-то
пойдёт не так, SSH пропадёт. Сиди за монитором шлюза.

## Шаг 1.6 - Контрольная перезагрузка №1

```
sudo reboot
```

После загрузки - четыре проверки, ПО ОДНОЙ.

Проверка первая - новые имена:

```
ip -br link
```

**ОЖИДАЕТСЯ:** есть интерфейсы `wan` и `lan`, старых имён `enp...` нет.

**ЕСЛИ остались старые имена** -> не сработала привязка. Проверь MAC в
`.link`-файлах (Шаг 1.4), повтори `sudo update-initramfs -u` и перезагрузись.

Проверка вторая - WAN получил адрес:

```
ip -br addr show wan
```

**ОЖИДАЕТСЯ:** `UP` и адрес от PON-терминала (например `192.168.0.x/24`).

**ЕСЛИ адреса нет** -> `sudo systemctl restart NetworkManager`, подожди 10 с,
повтори. Не помогло - проверь `nmcli device status`.

Проверка третья - LAN не под NetworkManager и с адресом:

```
nmcli device status
```

**ОЖИДАЕТСЯ:** `wan` - `connected` (профиль `Wired connection 1`), `lan` -
`unmanaged` (или "без управления").

```
ip -br addr show lan
```

**ОЖИДАЕТСЯ:** `192.168.50.1/24`. Статус может быть `DOWN`/`NO-CARRIER`,
пока в LAN не воткнут кабель, - это нормально.

Проверка четвёртая - не бегает старый DHCP-клиент:

```
pgrep -a dhclient
```

**ОЖИДАЕТСЯ:** пусто.

**ЕСЛИ что-то вывелось** -> в `/etc/network/interfaces` осталась живая строка
про карту (Шаг 1.5.2). Закомментируй и перезагрузись.

⛔ **СТОП:** дальше - только если все четыре проверки сошлись.

> **Реальный случай:** пропустили эту перезагрузку, потом несколько часов
> искали "баг в nftables", а сеть просто не переживала reboot из-за
> конкурирующего DHCP-клиента. Не пропускай.

## Шаг 1.7 - sysctl, firewall, NAT

### 1.7.1 - Пересылка пакетов, выключить IPv6, rp_filter

- `ip_forward=1` - без него клиенты вообще не пойдут через шлюз;
- `disable_ipv6` - вся схема IPv4, IPv6 утекал бы мимо полос;
- `rp_filter=2` - маршрутизация по меткам (Часть 2) в строгом режиме (1) не
  работает, ядро выбрасывает пакеты. Ставим нестрогий режим явно.

```
sudo tee /etc/sysctl.d/99-gateway.conf > /dev/null <<'EOF'
net.ipv4.ip_forward=1
net.ipv6.conf.all.disable_ipv6=1
net.ipv6.conf.default.disable_ipv6=1
net.ipv4.conf.all.rp_filter=2
net.ipv4.conf.default.rp_filter=2
EOF
```

```
sudo sysctl --system
```

**ПРОВЕРКА:**

```
sudo /usr/sbin/sysctl net.ipv4.ip_forward net.ipv6.conf.all.disable_ipv6 net.ipv4.conf.all.rp_filter
```

**ОЖИДАЕТСЯ:**

```
net.ipv4.ip_forward = 1
net.ipv6.conf.all.disable_ipv6 = 1
net.ipv4.conf.all.rp_filter = 2
```

### 1.7.2 - Firewall (`/etc/gw-fw.nft` + юнит `gw-fw`)

Правила, которые нельзя нарушать:
- штатный `nftables.service` и `/etc/nftables.conf` НЕ используем;
- НИКОГДА не пиши `flush ruleset`. Файл пересоздаёт только свою таблицу
  `inet gw_fw`;
- таблицу `ip nat` не трогаем (Docker, Tailscale).

```
sudo tee /etc/gw-fw.nft > /dev/null <<'EOF'
#!/usr/sbin/nft -f
# gw-fw: firewall входа в шлюз + forward. Хозяин: gw-fw.service.
# Пересоздаёт только свою таблицу - чужие (Docker, Tailscale, gwroute) не трогает.
table inet gw_fw
delete table inet gw_fw
table inet gw_fw {
    chain input {
        type filter hook input priority 0; policy drop;
        iif "lo" accept
        ct state established,related accept
        ct state invalid drop
        # LAN: администрирование (SSH), DNS, DHCP
        iifname "lan" accept
        # Tailscale: удалённый доступ
        iifname "tailscale0" accept
        # WAN: прямые соединения Tailscale
        iifname "wan" udp dport 41641 accept
        # WAN: продление DHCP от PON-терминала
        iifname "wan" udp sport 67 udp dport 68 accept
        # ICMP: ping, Path MTU Discovery
        meta l4proto { icmp, ipv6-icmp } accept
        # всё остальное на WAN, в том числе SSH 22 - policy drop
    }
    chain forward {
        type filter hook forward priority filter; policy accept;
        # MSS clamp: без него часть сайтов виснет через туннели (MTU)
        tcp flags syn tcp option maxseg size set rt mtu
        # DoT (порт 853) клиентов запрещён: иначе их DNS идёт мимо dnsmasq
        # и полосы не работают. Android с "Частным DNS" откатится на DNS шлюза.
        iifname "lan" tcp dport 853 reject with tcp reset
        iifname "lan" udp dport 853 reject
    }
}
EOF
```

> Что делают правила:
> - **SSH с WAN закрыт.** Вход - только из LAN и через Tailscale. Не
>   добавляй `iifname "wan" tcp dport 22 accept`: это открытая калитка для
>   сканеров.
> - **DoT 853.** Шифрованный DNS клиента прячет запросы от dnsmasq, и IP не
>   попадают в наборы - сайт уходит не в свою полосу, блок-листы не
>   работают. Режем, и устройство переходит на DNS шлюза.
>   ⚠️ Если на Android "Частный DNS" задан **конкретным именем** провайдера,
>   при закрытом 853 у этого устройства пропадёт интернет. Режимы
>   "Автоматически" и "Отключено" работают нормально.
> - DoH (DNS через 443) так не закрыть: он неотличим от обычного HTTPS.
>   Secure DNS в браузерах выключается руками (Часть 4).

```
sudo tee /etc/systemd/system/gw-fw.service > /dev/null <<'EOF'
[Unit]
Description=gw-fw host input firewall (gateway-aware)
Before=network-pre.target
Wants=network-pre.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/sbin/nft -f /etc/gw-fw.nft
ExecStop=/usr/sbin/nft delete table inet gw_fw

[Install]
WantedBy=multi-user.target
EOF
```

> `Before=network-pre.target` (а не `After=`): firewall встаёт ДО поднятия
> карт, без окна, когда WAN уже поднят, а защиты ещё нет.

```
sudo systemctl daemon-reload
```

```
sudo systemctl enable --now gw-fw
```

**ПРОВЕРКА:**

```
sudo nft list table inet gw_fw
```

**ОЖИДАЕТСЯ:** цепочка `input` с `policy drop` и цепочка `forward` с
правилом `maxseg` и двумя правилами про `853`.

**ЕСЛИ ошибка** -> `sudo systemctl status gw-fw`, частая причина - опечатка
при вставке файла.

⛔ **СТОП про SSH:** если сидишь по SSH из LAN, убедись, что сессия жива
(команды выполняются), прежде чем идти дальше.

### 1.7.3 - NAT (`gw-nat.sh` + юнит `gw-nat`)

NAT нужен, чтобы клиенты `192.168.50.x` выходили в интернет через `wan`.
Живёт в своей таблице `ip gw_nat`. NAT для туннелей добавится в Части 2.

> ⚠️ WAN здесь вписан явно (`wan`). НЕ переделывай на автоопределение по
> маршруту по умолчанию: в Части 2 маршрут для клиентов уходит в туннель, и
> автоопределение повесило бы NAT не туда.

```
sudo tee /usr/local/sbin/gw-nat.sh > /dev/null <<'EOF'
#!/bin/bash
# NAT шлюза: маскарад подсети LAN через физический WAN.
# WAN задан явно, без автоопределения по default route.
WAN=wan
nft delete table ip gw_nat 2>/dev/null
nft -f - <<NFT
table ip gw_nat {
    chain postrouting {
        type nat hook postrouting priority srcnat; policy accept;
        ip saddr 192.168.50.0/24 oifname "$WAN" masquerade
    }
}
NFT
echo "gw_nat applied: 192.168.50.0/24 -> $WAN"
EOF
```

```
sudo chmod 755 /usr/local/sbin/gw-nat.sh
```

```
sudo tee /etc/systemd/system/gw-nat.service > /dev/null <<'EOF'
[Unit]
Description=gw-nat: masquerade LAN via WAN
After=network-pre.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/gw-nat.sh
ExecStop=/usr/sbin/nft delete table ip gw_nat

[Install]
WantedBy=multi-user.target
EOF
```

```
sudo systemctl daemon-reload
```

```
sudo systemctl enable --now gw-nat
```

**ОЖИДАЕТСЯ:** строка `gw_nat applied: 192.168.50.0/24 -> wan`.

**ПРОВЕРКА:**

```
sudo nft list table ip gw_nat
```

**ОЖИДАЕТСЯ:** правило `ip saddr 192.168.50.0/24 oifname "wan" masquerade`.

**ЕСЛИ там буквально `oifname "$WAN"`** - в скрипте перед `$WAN` стоит
обратная косая черта (`\$WAN`), и переменная не подставляется. Правило
тогда мёртвое: сразу после загрузки, пока не встанет `gwroute`, клиенты
выходят без NAT (в журнале ядра `martian source 192.168.50.x ... on dev wan`).
Исправить:

```
sudo sed -i 's/\\\$WAN/$WAN/g' /usr/local/sbin/gw-nat.sh
```

```
sudo systemctl restart gw-nat
```

и повторить проверку.

## Шаг 1.8 - DHCP и DNS для клиентов (dnsmasq)

dnsmasq раздаёт клиентам адреса и работает их DNS-сервером. В Части 2 он же
раскладывает домены по наборам.

```
sudo tee /etc/dnsmasq.d/lan.conf > /dev/null <<'EOF'
interface=lan
# bind-dynamic, НЕ bind-interfaces: жёсткий bind падает, если при старте
# dnsmasq у lan ещё нет адреса (гонка при загрузке).
bind-dynamic
dhcp-range=192.168.50.50,192.168.50.150,12h
dhcp-option=option:router,192.168.50.1
dhcp-option=option:dns-server,192.168.50.1
domain-needed
bogus-priv
# Запросы уходят в dnscrypt-proxy (Шаг 1.9) на порт 5300
no-resolv
server=127.0.0.1#5300
# IPv6 выключен - не отдавать клиентам AAAA, иначе они ждут таймаут
filter-AAAA
EOF
```

Журнал запросов (нужен для проверок и диагностики):

```
sudo tee /etc/dnsmasq.d/zz-logqueries.conf > /dev/null <<'EOF'
log-queries
EOF
```

**ПРОВЕРКА синтаксиса:**

```
sudo dnsmasq --test
```

**ОЖИДАЕТСЯ:** `dnsmasq: syntax check OK.`

> ⚠️ **Ловушка dnsmasq.** Он читает **каждый** файл в `/etc/dnsmasq.d/`,
> кроме `.dpkg-dist/.dpkg-old/.dpkg-new`. Файл `*.bak` или `*.disabled` там
> **продолжает работать**. Бэкапы держи в `/root/`.

> **Постоянный адрес для устройства** (приставка, ПК, консоль) - строка
> `dhcp-host=MAC,IP` в отдельном файле, например
> `/etc/dnsmasq.d/02-static.conf`:
> `dhcp-host=aa:bb:cc:dd:ee:ff,192.168.50.77`. Адрес бери ВНЕ диапазона
> `.50-.150`.

**Автоподъём dnsmasq.** Штатная служба после сбоя сама не поднимается, а без
неё у всей локалки нет DNS (найдено на учениях, Часть 4 раздел 13):


```
printf '[Service]\nRestart=always\nRestartSec=2\n' | sudo tee /etc/systemd/system/dnsmasq.service.d/restart.conf
```

```
sudo systemctl daemon-reload
```

dnsmasq пока НЕ перезапускаем - сначала dnscrypt.

## Шаг 1.9 - Шифрованный DNS (dnscrypt-proxy, вручную)

Обычный DNS ТСПУ видит и может подменять. dnscrypt-proxy шифрует запросы,
dnsmasq ходит в него на `127.0.0.1:5300`.

> Ставим вручную: в Debian версия старая. Плата - обновлять самому (1.9.6).

### 1.9.1 - Узнать актуальную версию

посмотри номер последнего релиза. Ниже пример для `2.1.17`. ⛔ Если вышла
новее - подставь её номер во ВСЕ команды шага (три места в 1.9.2).

### 1.9.2 - Скачать и установить

```
cd /tmp && curl -fsSLO https://github.com/DNSCrypt/dnscrypt-proxy/releases/download/2.1.17/dnscrypt-proxy-linux_x86_64-2.1.17.tar.gz
```

**ОЖИДАЕТСЯ:** молчание (тихий режим curl) - это нормально.

```
cd /tmp && tar xzf dnscrypt-proxy-linux_x86_64-2.1.17.tar.gz
```

```
sudo install -m755 /tmp/linux-x86_64/dnscrypt-proxy /usr/local/bin/dnscrypt-proxy
```

```

```

**ОЖИДАЕТСЯ:** номер версии.

**ЕСЛИ `No such file`** -> скачивание не прошло. Проверь `ping -c2 1.1.1.1`,

### 1.9.3 - Конфиг

Резолверы зашиты статичными штампами (без онлайн-списка, который сам можно
заблокировать). AdGuard - заодно режет рекламу. Два сервера на **разных
адресах**, dnscrypt-proxy сам берёт тот, что отвечает:

- DoH на `94.140.14.14` - напрямую через провайдера;
- DNSCrypt на `94.140.15.15` - после Части 2 через туннель (правило
  `priority 9400` в `gw-routing-restore.sh`). ТСПУ режет DoH/DoT по IP и по
  протоколу (осень 2026: NextDNS и др.) - тогда DNS живёт через туннель, а
  умрут оба туннеля - через прямой.

У DoH в штампе **нет отпечатка сертификата**, сертификат проверяется по имени
`dns.adguard-dns.com`, как в браузере. Старый штамп с отпечатком сломался,
когда AdGuard сменил сертификат (`Certificate hash ... not found`), и DNS
неделями держался на одном DNSCrypt.

```
sudo mkdir -p /etc/dnscrypt-proxy
```

```
sudo tee /etc/dnscrypt-proxy/dnscrypt-proxy.toml > /dev/null <<'EOF'
## dnscrypt-proxy: шифрованный upstream для dnsmasq. Слушает только 127.0.0.1:5300.
listen_addresses = ['127.0.0.1:5300']
max_clients = 250
ipv6_servers = false
block_ipv6 = true
dnscrypt_servers = true
doh_servers = true
require_dnssec = false
require_nolog = false
require_nofilter = false
server_names = ['adguard-doh', 'adguard-dnscrypt']
force_tcp = false
timeout = 5000
keepalive = 30
cache = true
cache_size = 4096
cache_min_ttl = 600
cache_max_ttl = 86400
log_level = 2
ignore_system_dns = true
netprobe_address = '94.140.14.14:53'
netprobe_timeout = 60
bootstrap_resolvers = ['94.140.14.14:53', '94.140.15.15:53']
[static]
  [static.adguard-doh]
  stamp = 'sdns://AgMAAAAAAAAADDk0LjE0MC4xNC4xNAATZG5zLmFkZ3VhcmQtZG5zLmNvbQovZG5zLXF1ZXJ5'
  [static.adguard-dnscrypt]
  stamp = 'sdns://AQMAAAAAAAAAETk0LjE0MC4xNS4xNTo1NDQzINErR_JS3PLCu_iZEIbq95zkSV2LFsigxDIuUso_OQhzIjIuZG5zY3J5cHQuZGVmYXVsdC5uczEuYWRndWFyZC5jb20'
EOF
```

> `cache_min_ttl = 600` держит ответы минимум 10 минут. Если сайт сменил IP,
> старый адрес может жить в кэше до 10 минут (плюс кэш самого AdGuard). Это
> нормально, лечится ожиданием или перезапуском dnscrypt-proxy и dnsmasq.

### 1.9.5 - ⛔ Ловушка: DNS самого шлюза утекает мимо dnscrypt

На шлюзе два DNS-механизма: dnsmasq (для клиентов, через dnscrypt - всё
хорошо) и **systemd-resolved** (для самого шлюза). Resolved по умолчанию
берёт DNS провайдера с WAN, и собственные запросы шлюза идут открытым
текстом. Клиенты при этом работают, поэтому утечку не видно.

**ПРОВЕРКА:**

```
resolvectl status | grep -iE 'Current DNS|DNS Servers'
```

**ОЖИДАЕТСЯ (здоровое состояние):** везде только `127.0.0.1`. Тогда пропусти
фикс.

**ЕСЛИ видишь другие адреса** -> фикс, по одной:

```
sudo mkdir -p /etc/systemd/resolved.conf.d
```

```
sudo tee /etc/systemd/resolved.conf.d/00-dnsmasq.conf > /dev/null <<'EOF'
[Resolve]
DNS=127.0.0.1
Domains=~.
FallbackDNS=
EOF
```

```
sudo nmcli con mod "Wired connection 1" ipv4.ignore-auto-dns yes ipv4.dns 127.0.0.1
```

⚠️ Следующая команда на секунду оборвёт WAN:

```
sudo nmcli con up "Wired connection 1"
```

```
sudo systemctl restart systemd-resolved
```

**ПРОВЕРКА после фикса:** повтори `resolvectl status | grep -iE 'Current DNS|DNS Servers'`
(везде `127.0.0.1`) и `dig +short ya.ru @127.0.0.1` (есть IP).

**ЕСЛИ резолвинг пропал** -> откат, по одной:
`sudo rm /etc/systemd/resolved.conf.d/00-dnsmasq.conf`,
`sudo nmcli con mod "Wired connection 1" ipv4.ignore-auto-dns no ipv4.dns ""`,
`sudo nmcli con up "Wired connection 1"`, `sudo systemctl restart systemd-resolved`.

### 1.9.6 - Обновление dnscrypt-proxy (раз в несколько месяцев)

Автообновления у него нет. Бэкап рабочего бинарника:

```

```

Дальше повтори 1.9.2 с новым номером версии, затем
`sudo systemctl restart dnscrypt-proxy` и `dig +short example.com @127.0.0.1`.

Откат: `sudo install -m755 /root/dnscrypt-proxy-СТАРАЯ.backup /usr/local/bin/dnscrypt-proxy`
и рестарт. Конфиг при обновлении не трогается.

## Шаг 1.10 - Принудительный DNS шлюза для клиентов (gw-dnsredirect)

Если клиент жёстко прописал себе чужой DNS (`8.8.8.8` и т.п.), его запросы
обходят dnsmasq, и полосы для него не работают. Этот юнит перехватывает
любой обычный DNS (порт 53) из LAN и отдаёт его dnsmasq.

```
sudo tee /etc/gw-dnsredirect.nft > /dev/null <<'EOF'
#!/usr/sbin/nft -f
# Заворот DNS клиентов LAN (порт 53) на локальный dnsmasq. Пересоздаёт только свою таблицу.
add table ip gw_dnsredirect
delete table ip gw_dnsredirect
table ip gw_dnsredirect {
    chain prerouting {
        type nat hook prerouting priority dstnat; policy accept;
        iifname "lan" udp dport 53 redirect to :53
        iifname "lan" tcp dport 53 redirect to :53
    }
}
EOF
```

```
sudo tee /etc/systemd/system/gw-dnsredirect.service > /dev/null <<'EOF'
[Unit]
Description=Force LAN DNS to local dnsmasq (anti-spoof redirect)
After=dnsmasq.service
Wants=dnsmasq.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/sbin/nft -f /etc/gw-dnsredirect.nft
ExecStop=/usr/sbin/nft delete table ip gw_dnsredirect

[Install]
WantedBy=multi-user.target
EOF
```

```
sudo systemctl daemon-reload
```

```
sudo systemctl enable --now gw-dnsredirect
```

**ПРОВЕРКА:**

```
sudo nft list table ip gw_dnsredirect
```

**ОЖИДАЕТСЯ:** два правила `redirect to :53`.

> Вместе с блокировкой 853 (Шаг 1.7.2) это закрывает обычный DNS и DoT.
> Остаётся DoH в браузерах - только ручное отключение на клиенте.

## Защита шлюза от устройств в LAN (сделай заранее)

Дешёвые Android-приставки, "умные" устройства и чужие ноутбуки в домашней
сети - реальный риск. Реальный случай: китайская ТВ-приставка из коробки
шла с открытым ADB (отладка Android по сети, порт 5555) и фоновыми службами,
которые стучались на десятки мусорных доменов. Через такую приставку можно
атаковать сам шлюз, если на нём открыты службы для всей LAN.

**1. Посмотри, что шлюз слушает для всех:**

```
sudo ss -tlnp | grep -v '127.0.0.1' | tee /tmp/listen.txt
```

Всё, что слушает `0.0.0.0` или `*`, доступно из LAN (правило
`iifname "lan" accept`). Панели, базы, служебные контейнеры, которым LAN не
нужна, - закрой.

**2. Закрыть порты из LAN** - правило в цепочку `input` **перед** строкой
`iifname "lan" accept`. Пример для портов 5678 и 8100 (подставь свои из
вывода выше):

```
        iifname "lan" tcp dport { 5678, 8100 } drop
```

Вписывай в `/etc/gw-fw.nft` (не в рантайм), потом
`sudo nft -f /etc/gw-fw.nft`. Перезагрузка файла безопасна - он пересоздаёт
только свою таблицу.

**3. Подозрительное устройство - только DNS и DHCP.** Разрешаем ему к шлюзу
лишь DNS (53) и DHCP (67), остальное режем. Три строки перед
`iifname "lan" accept`, ⛔ MAC подставь его:

```
        ether saddr ПОДСТАВЬ_MAC_УСТРОЙСТВА udp dport { 53, 67 } accept
        ether saddr ПОДСТАВЬ_MAC_УСТРОЙСТВА tcp dport 53 accept
        ether saddr ПОДСТАВЬ_MAC_УСТРОЙСТВА drop
```

Интернет у устройства останется: это цепочка `input` (обращения к самому
шлюзу), а не `forward`.

**4. Мусорные домены - в "чёрную дыру" dnsmasq**, файл
`/etc/dnsmasq.d/08-block.conf`, строка на домен:

```
address=/пример-мусорного-домена.xyz/0.0.0.0
```

После правки: `sudo dnsmasq --test`, затем `sudo systemctl restart dnsmasq`.

**5. ADB на Android-устройствах** проверяй с ПК:
`adb connect IP_УСТРОЙСТВА:5555`. Подключилось без запроса на экране -
отладка открыта всем. Команда `adb usb` закрывает сетевой ADB до
перезагрузки устройства. Часть прошивок открывает его снова при каждом
старте.

## Чего на шлюзе быть НЕ должно (антислои)

Каждый пункт - реальный лишний слой, найденный аудитом. Тихо лежит и
"стреляет" при перезагрузке или обновлении. Все проверки только читают.

1. **netfilter-persistent / iptables-persistent** - восстанавливает старые
   дампы iptables.
   `systemctl is-enabled netfilter-persistent 2>&1` -> `disabled` или "не
   найден". Файлы `/etc/iptables/rules.v4/v6` - в архив вне `/etc`.
2. **UFW.** `command -v ufw` -> пусто.
3. **Штатный nftables.service.** `systemctl is-enabled nftables 2>&1` ->
   `disabled`.
4. **systemd-networkd.** `systemctl is-enabled systemd-networkd 2>&1` ->
   `disabled`. В `/etc/systemd/network/` - только `10-wan.link` и
   `10-lan.link`, никаких `*.network`/`*.netdev`.
5. **Живые записи ifupdown.** `grep -E "auto|iface" /etc/network/interfaces`
   -> живые строки только про `lo`.
6. **Профили NetworkManager для LAN.**
   `nmcli -f NAME,DEVICE,AUTOCONNECT con show` -> профиль только у `wan`.
7. **Осиротевшие бинарники старых стеков** (sing-box, tun2socks, zapret и
   т.п.) в `/usr/local/bin`, `/opt` - в архив.
8. **Резервные копии в `/etc/dnsmasq.d/`.**
   `ls /etc/dnsmasq.d/ | grep -iE '\.bak|\.disabled|\.save|\.old'` -> пусто.

## Если что-то пошло не так

- **Сначала проверь, что предыдущий шаг реально сошёлся**, только потом
  подозревай текущий.
- **Потерял SSH** (заблокировал себя firewall): нужен монитор и клавиатура.
  `sudo nft list table inet gw_fw` - должно быть `iifname "lan" accept`.
  Нет - `sudo systemctl restart gw-fw`.
- **Пропал интернет у всех клиентов** - NAT или пересылка:
  `sudo nft list table ip gw_nat` и
  `sudo /usr/sbin/sysctl net.ipv4.ip_forward` (`= 1`).
- **После переноса сетевой карты в другой слот всё отвалилось** - проверь
  `ip -br link`. Видишь `enp...` вместо `wan`/`lan` - `.link`-файл не
  совпал по MAC (Шаг 1.4).
