# ЧАСТЬ 9 - Шлюз напрямую к провайдеру по PPPoE (логин и пароль)

> **Что получится:**
> - кабель провайдера включён прямо в WAN шлюза, роутер провайдера не нужен;
> - шлюз сам поднимает PPPoE-сессию и переподключается при обрывах;
> - **все остальные части работают без правок**: PPP-интерфейс называется
>   `wan`, как раньше называлась сетевая карта, поэтому NAT, фаервол, полосы,
>   `warp-pick`, `netwatch` его "не замечают";
> - переключение безопасно для удалённой точки: если PPPoE не заработал за
>   20 минут, **страж сам откатывает** шлюз на DHCP и перезагружает.
>
> **Правила для ИИ - в Части 0.** Все команды - **на шлюзе**, если не сказано
> иное. ⛔ Логин и пароль PPPoE **никогда не присылать в чат** и не писать в
> команды - их спрашивает скрипт сам.
>
> **Скрипт:** `tools/gw-pppoe.sh` из репозитория. Он делает всё ниже сам, а
> эта часть объясняет, что он делает, как проверить и как чинить руками.

---

## Шаг 9.0 - Подходит ли это подключение

| Что приходит от провайдера | Что делать |
|---|---|
| медный кабель RJ45, в договоре логин и пароль PPPoE | эта часть |
| медный кабель RJ45, интернет "сам" (DHCP / IPoE) | ничего: шлюз уже так работает |
| оптика (PON) | терминал провайдера в режиме моста (bridge), или свой GPON-стик вместо терминала (**сначала Шаг 9.6**), затем эта часть |

Узнать заранее у провайдера или в настройках старого роутера:
1. **Логин и пароль PPPoE.** Они в договоре; если нет - поддержка провайдера.
2. **Нужен ли VLAN** (номер тега). На медном кабеле в квартиру обычно не
   нужен; если в роутере в настройках WAN стоит "VLAN ID" - запиши число.
3. **Привязка по MAC.** Если провайдер пускает только MAC старого роутера -
   запиши MAC его WAN-порта (наклейка на дне или страница статуса).

### 9.0.1 - Предусловия на шлюзе

```
sudo bash /usr/local/sbin/gw-pppoe.sh check
```

(Если скрипта ещё нет на шлюзе - сначала шаг 9.1, первая команда.)

**ОЖИДАЕТСЯ:** все строки `OK`, в конце `ГОТОВО к prepare`.

| FAIL | Что значит | Лечение |
|---|---|---|
| NetworkManager не работает | сеть настроена иначе | эта часть не подходит; разбирать отдельно |
| WAN описан в `/etc/network/interfaces` | сеть через ifupdown | то же |
| нет `.link` с `Name=wan` | имя карты не закреплено по MAC | ниже, 9.0.2 |
| нет активного профиля на `wan` | WAN сейчас без адреса | сначала добиться интернета по DHCP (Часть 1) |

### 9.0.2 - Закрепить имя WAN по MAC (только если `check` попросил)

MAC физической WAN-карты:

```
ip -br link show wan
```

Второй столбец после `UP` - MAC вида `aa:bb:cc:dd:ee:ff`.

⛔ Подставь **свой** MAC вместо `ПОДСТАВЬ_MAC_WAN`:

```
printf '[Match]\nMACAddress=ПОДСТАВЬ_MAC_WAN\n\n[Link]\nName=wan\n' | sudo tee /etc/systemd/network/10-wan.link
```

```
sudo update-initramfs -u
```

Перезагрузка и `check` ещё раз.

## Шаг 9.1 - Подготовка (`prepare`): сеть не меняется

Можно делать удалённо, пока шлюз ещё стоит **за старым роутером** и получает
интернет по DHCP.

Скопировать скрипт на шлюз (**с ПК, PowerShell**; путь к файлу - свой):

```
scp d:\server\gw-pppoe.sh ЛОГИН@АДРЕС_ШЛЮЗА:/tmp/
```

**На шлюзе.** Без VLAN и без подмены MAC:

```
sudo bash /tmp/gw-pppoe.sh prepare
```

С VLAN (пример - тег 10) и/или MAC старого роутера:

```
sudo bash /tmp/gw-pppoe.sh prepare --vlan 10 --mac AA:BB:CC:DD:EE:FF
```

Скрипт спросит логин и дважды пароль - **вводит человек сам**, на экран
пароль не выводится.

**ОЖИДАЕТСЯ** в конце: `ГОТОВО. Сеть не менялась.`

Что сделал `prepare`:
1. поставил пакет `ppp` (нужен NetworkManager для PPPoE);
2. скопировал себя в `/usr/local/sbin/gw-pppoe.sh`;
3. создал **выключенные** профили NetworkManager:
   - `gw-pppoe` - боевой: PPP-интерфейс `wan` поверх карты `wanphy`,
     MTU/MRU 1492, проверка связи каждые 10 с (после 6 пропусков - переподключение),
     переподключаться **бесконечно** (`autoconnect-retries 0`), IPv6 выключен;
   - `gw-pppoe-test` - для пробы: интерфейс `ppptest` поверх текущей `wan`,
     **без** маршрута по умолчанию и без DNS провайдера;
   - при `--vlan` - ещё VLAN-профили;
4. поправил два скрипта шлюза (бэкапы - в `/var/lib/gw-pppoe/backup-*`):
   - `vpn-slot-up.sh` - пин адреса туннеля к WAN работал только при шлюзе
     вида `via 192.168.x.1`; у PPPoE шлюза нет - теперь маршрут ставится
     через интерфейс;
   - `gw-routing-restore.sh` - подрезка MSS добавлена и для `wan` (у PPPoE
     MTU 1492 вместо 1500; без подрезки "висят" некоторые сайты);
5. поставил службу-стража `gw-pppoe-guard` (молчит, пока нет пробного режима).

> **Если `prepare` написал "не совпал с ожидаемым текстом"** - скрипт шлюза
> отличается от эталона, правка не сделана (файл не тронут). Вручную:
> - в `vpn-slot-up.sh` строку с `WAN_GW_R=` заменить так, чтобы шлюз брался
>   из слова после `via`, а при пустом шлюзе ставить
>   `ip route replace "$EP_IP/32" dev "$WAN_IF_R"`;
> - в `gw-routing-restore.sh` в строке `nft add rule ip gwroute mss oifname { ... }`
>   добавить в список `"wan"`.

## Шаг 9.2 - Проба (`test`): проверить логин и пароль, ничего не ломая

```
sudo gw-pppoe.sh test
```

Поднимает пробную PPPoE-сессию **рядом** с текущей сетью: интернет дома в
это время идёт как обычно.

**ОЖИДАЕТСЯ:** `PPPoE ПОДНЯЛСЯ: адрес ...` и `интернет через PPPoE: ЕСТЬ`.

Когда проба возможна:
- шлюз стоит **за роутером с функцией PPPoE passthrough** ("PPPoE relay",
  "PPPoE pass-through" - включить в настройках роутера); или
- кабель провайдера временно воткнут прямо в WAN шлюза.

| Сообщение | Значит |
|---|---|
| `Timeout waiting for PADO` | PPPoE не доходит до провайдера: у роутера нет passthrough или нужен VLAN |
| `authentication failed`, CHAP/PAP | неверный логин или пароль -> снова `prepare` |
| сессия занята / роутер отвалился | провайдер даёт **одну сессию на логин** - пробовать при выключенном роутере |

> Проба необязательна: без неё `enable` всё равно безопасен благодаря стражу.

## Шаг 9.3 - Переключение (`enable`)

⛔ **СТОП.** Перед этим:
- старый роутер провайдера **оставить на месте и не сбрасывать** - это путь
  отката для человека без знаний;
- договориться с человеком на месте, что он переткнёт кабель (ниже);
- у шлюза должен быть живой Tailscale - по нему ты вернёшься после переключения.

```
sudo gw-pppoe.sh enable
```

Скрипт попросит ввести `ДА` и перезагрузит шлюз. После загрузки:
- карта WAN называется `wanphy`, на ней поднимается PPPoE-интерфейс `wan`;
- DHCP на WAN выключен;
- **страж** 20 минут ждёт интернет через PPPoE. Есть 3 удачных проверки
  подряд - режим закрепляется. Нет за 20 минут - **сам откат на DHCP** и
  перезагрузка.

Дольше окно (например, человеку на месте нужно больше времени):

```
sudo gw-pppoe.sh enable --guard-min 40
```

**Инструкция человеку на месте** (переслать как есть):
1. Найди кабель провайдера (тот, что приходит из подъезда) - он сейчас в
   гнезде **WAN / Internet** старого роутера.
2. Вынь его и воткни в гнездо **WAN** шлюза (то, где сейчас кабель от
   старого роутера).
3. Старый роутер **выключи из розетки**.
4. Подожди 5 минут и проверь интернет.
5. Если через 30 минут интернета нет - верни как было: кабель провайдера в
   WAN старого роутера, кабель шлюза в LAN роутера, роутер включи.

> Почему роутер выключать: провайдер может держать его старую сессию ещё
> несколько минут и не пускать вторую с тем же логином. У одного провайдера
> наблюдали "остывание" около 4 минут. Поэтому окно стража - 20 минут, а не 5.

**После переключения** (по Tailscale):

```
sudo gw-pppoe.sh status
```

**ОЖИДАЕТСЯ:** `режим WAN: pppoe`, `закреплено: <дата>`, у `wan` адрес
провайдера, MTU 1492, маршрут `default dev wan ...`.

Полосы (все должны дать `200`):

```
for i in wan vpn-main vpn-backup vpn-amz; do printf '%-11s ' $i; curl -s -o /dev/null -m 8 -w '%{http_code}\n' --interface $i https://cloudflare.com/cdn-cgi/trace || echo; done
```

Крупные пакеты через туннели (у PPPoE на 8 байт меньше MTU):

```
for i in vpn-main vpn-backup; do printf '%-11s ' $i; ping -c2 -W3 -M do -s 1200 -I $i 1.1.1.1 >/dev/null 2>&1 && echo OK || echo "НЕ ПРОХОДИТ"; done
```

> Эту же проверку сделай **до** `enable`, пока WAN на DHCP: если и тогда
> было `НЕ ПРОХОДИТ` - на пути режется ICMP, а не MTU, и результат после
> переключения ни о чём не говорит.

`НЕ ПРОХОДИТ` после переключения, а до было `OK` -> уменьшить `MTU` в
конфиге этого туннеля на 8-20 и перезапустить слот (Часть 2).

> Отчёт после загрузки (`bootcheck`) может ругаться `WAN-IP`: адрес теперь
> выдаёт провайдер, и он меняется. Поправь там ожидаемый адрес или проверку.

## Шаг 9.4 - Откат на DHCP (`disable`)

Вернуть "как было" (кабель провайдера снова в старый роутер, шлюз - за ним):

```
sudo gw-pppoe.sh disable
```

Перезагрузка, карта снова `wan`, DHCP включён, PPPoE выключен. Профили и
логин/пароль остаются - можно включить снова без `prepare`.

**Аварийно, без скрипта, за монитором шлюза:**
1. в `/etc/systemd/network/10-wan.link` (или в том `.link`, где `Name=wanphy`)
   заменить `Name=wanphy` на `Name=wan`, удалить строки `# gw-pppoe-mac` и
   `MACAddress=` под `[Link]`;
2. `sudo rm -f /etc/NetworkManager/conf.d/90-gw-pppoe.conf /var/lib/gw-pppoe/trial`;
3. `sudo nmcli connection modify gw-pppoe connection.autoconnect no`;
4. `sudo nmcli connection modify "Wired connection 1" connection.autoconnect yes`
   (имя профиля - `cat /var/lib/gw-pppoe/dhcpprofile`);
5. `sudo update-initramfs -u` и `sudo reboot`.

## Шаг 9.5 - Сменить логин или пароль PPPoE

Логин:

```
sudo nmcli connection modify gw-pppoe pppoe.username НОВЫЙ_ЛОГИН
```

Пароль (спросит, на экран не выведет):

```
read -rsp 'Пароль PPPoE: ' P; echo; sudo nmcli connection modify gw-pppoe pppoe.password "$P"; unset P
```

Применить:

```
sudo nmcli connection up gw-pppoe
```

(Для пробного профиля - то же с `gw-pppoe-test`.)

## Диагностика

| Симптом | Проверка | Лечение |
|---|---|---|
| после `enable` шлюз пропал, через 20-30 мин вернулся | `sudo gw-pppoe.sh status` -> "последний откат стража" | читать `/var/lib/gw-pppoe/last-fail.log`: PADO - кабель/VLAN, auth - логин/пароль |
| `wan` есть, адреса нет | `journalctl -b \| grep -iE 'pppd\|pppoe' \| tail -30` | как в таблице шага 9.2 |
| PPPoE поднялся, часть сайтов "висит" | `sudo nft list chain ip gwroute mss` - есть ли `"wan"` | шаг 9.1, правка MSS |
| туннели не поднимаются после переключения | `ip route \| grep -E '162\.159\|10\.78'` - пин адреса туннеля | правка `vpn-slot-up.sh` (9.1), `sudo systemctl restart vpn-slot@vpn-main` |
| интернет рвётся раз в сутки на минуту | `journalctl -t NetworkManager \| grep -i ppp` | это часто плановый разрыв сессии у провайдера; переподключение автоматическое |
| PPPoE не поднимается после смены роутера на шлюз | роутер ещё включён? | выключить роутер, подождать 5 мин (одна сессия на логин) |
| на `wanphy` появился DHCP-профиль "Wired connection 2" | `nmcli connection show` | `ls /etc/NetworkManager/conf.d/90-gw-pppoe.conf` - должен быть; удалить лишний профиль |

## Шаг 9.6 - Своя оптическая вставка (GPON-стик) вместо терминала провайдера

> **Когда это нужно.** Провайдер приходит в квартиру **оптикой** (PON), и
> сейчас в неё включён его терминал (ONT/ONU). Чтобы убрать терминал и завести
> оптику прямо в шлюз, в слот шлюза ставится **GPON-стик** (SFP-модуль-ONU) -
> маленькая "флешка" с оптическим входом. Для шлюза стик выглядит как обычная
> сетевая карта, а дальше идёт та же PPPoE из Шагов 9.1-9.3.
>
> ⛔ **Это необязательный и необратимый по времени шаг.** Терминал провайдера
> **не выбрасывать** - он единственный путь отката, вставил обратно и всё
> работает. Делать только когда есть физический доступ к железу и запас
> времени: с первого раза станция пускает не всегда.
>
> ⛔ Серийный номер, пароль PLOAM и логин PPPoE - **в чат не присылать**,
> только заглушки. Это ключи от твоего подключения.

### 9.6.0 - Что нужно из железа

| Деталь | Зачем | На что смотреть |
|---|---|---|
| GPON-стик (SFP-ONU) под твою сеть | принимает оптику вместо терминала | чип RTL960x популярен и прошиваем (напр. DFP-34X-2C2) |
| SFP-карта в слот PCIe шлюза | даёт шлюзу SFP-гнездо под стик | должна пускать **любой** SFP без привязки по vendor и уметь 1 Гбит/с по SFP (1000base-X и/или SGMII); совместимость конкретной карты со стиком заранее **не гарантируется**, проверяется только на месте |
| переходник **SC/APC - SC/UPC** | оптика провайдера обычно APC (зелёный), гнёзда стиков - UPC | у тебя он в комплекте стика |

> Подойдёт любой свободный слот **PCIe** (даже x16 Gen2 с запасом - SFP-карте
> хватает одной линии). Какие карты берут именно этот стик, надёжно заранее
> не известно (проверенных данных по каждой модели нет). Карты, жёстко
> привязанные к "своим" модулям (брендовые), могут не завестись. Всё это
> проверяется только на месте: сначала вставить стик **без изменения его
> настроек** и посмотреть линк (Шаг 9.6.2, п.2).

### 9.6.1 - Снять параметры со старого терминала (пока он работает)

Зайти в веб-панель терминала (у Ростелекома часто `http://192.168.0.1`,
логин обычно на наклейке) и **переписать себе** (не в чат):

| Параметр | Где в панели | Куда пойдёт |
|---|---|---|
| Серийный номер (GPON SN) | наклейка на дне + статус PON | в стик (`GPON_SN`) |
| Пароль **PLOAM** | раздел GPON / регистрация | в стик (`GPON_PLOAM_PASSWD`) |
| VLAN интернета | WAN / статус (в отчётах по Ростелекому - HSI, тег **10**, PPPoE; номер зависит от региона, **брать из WAN-страницы своего терминала**) | в PPPoE (Шаг 9.1, `--vlan`) |
| VLAN служебный (TR-069) | WAN | обычно не нужен шлюзу, но записать |
| Логин/пароль **PPPoE** | договор или WAN-настройки | в PPPoE (Шаг 9.2) |

> **Своё оборудование.** Если терминал твой (куплен, не арендован), в стик
> можно вписать **его же** SN и PLOAM - станция их уже знает, перепривязка и
> звонок в поддержку не нужны. Если оборудование провайдера или BYO не
> оформлен - вписывают **собственный SN стика** (с его наклейки) и звонят в
> поддержку: "своё оборудование, перепривяжите линию на этот серийник".
> ⛔ **Нельзя держать в оптике и терминал, и стик с одним SN одновременно** -
> станция запутается. Одно устройство на линии.
>
> **Позиция провайдера.** Поддержка Ростелекома нередко отвечает шаблоном
> "только наше оборудование" и чужой ONT официально не подключает (так писали
> в обсуждениях на форумах, регион не всегда указан). Часть людей переносит SN
> рабочего терминала в свой ONT и оставляет терминал про запас. Это решение
> и риск владельца линии: не подтверждено, что провайдер этого не заметит
> (стик в OMCI называет вендора по-своему, см. 9.6.2, п.3).

### 9.6.2 - Настроить стик

Команды ниже взяты со страницы модели в [hack-gpon](https://hack-gpon.org/ont-odi-realtek-dfp-34x-2c2/)
и из гайда [yashau/odi-dfp34x-gpon-stick](https://github.com/yashau/odi-dfp34x-gpon-stick)
(оба прочитаны 12.11.2026). **Сверять со страницей своей модели и версии
прошивки:** заводские значения у версий отличаются (например, `LAN_SDS_MODE`
по умолчанию `3` на hack-gpon для DFP-34X-2C2 и `1` в гайде yashau для 2C3).
Формат PLOAM и серийный номер - только по своим данным из 9.6.1, в чат не слать.

⛔ **Три запрета:**
- **не менять `ELAN_MAC_ADDR` и `MAC_KEY`:** ключ привязан к MAC, при несовпадении
  станция не авторизует стик (состояние O0, лазер выключен);
- **не ставить `LAN_SDS_MODE`, который не поддерживает хост** - стик станет
  недоступен по сети, лечится только консолью UART (ниже);
- после `mib commit` **подождать несколько секунд** до перезагрузки, команда
  асинхронная, иначе изменение теряется.

**1. Вставить стик в SFP-карту, пока без оптики и без смены настроек.**
Посмотреть линк:

```
ethtool ПОРТ_С_СТИКОМ
```

```
dmesg | grep -i bnx2x | tail -20
```

У стика свой адрес и своя подсеть (у нашего - `192.168.10.1/24`). Хосту нужен
адрес **из той же подсети**, иначе стик отвечает на ARP, но не на ping и веб:
на гнездо карты временно дать адрес вида `192.168.10.2/24`.

**2. Линк есть - режим не трогать, идти к п.3. Линка нет - см. "Режим
`LAN_SDS_MODE`" ниже, сначала подготовив UART.**

**3. Вписать идентичность** (по SSH или через веб-панель; логин и пароль
заводские `admin` / `admin`; SSH у стика старый и пускает по одному сеансу:
`ssh -oKexAlgorithms=+diffie-hellman-group1-sha1 -oCiphers=+3des-cbc -o HostKeyAlgorithms=ssh-rsa admin@АДРЕС_СТИКА`).
Формат из гайда (`VVVV` - 4 буквы вендора, `xxxxxxxx` - 8 hex-цифр SN):

```
flash set GPON_SN VVVVxxxxxxxx
```

```
flash set PON_VENDOR_ID VVVV
```

```
flash set GPON_PLOAM_PASSWD 00000000000000000000
```

(`HW_SERIAL_NO` в гайде задаётся как hex от `VVVV` плюс `xxxxxxxx`.) PLOAM -
hex без `0x` и разделителей; на прошивках от 220304 по telnet/SSH принимается
только hex, веб-панель берёт и ASCII. Потом:

```
mib commit
```

Проверка (ждём в конце состояние **O5**):

```
diag gpon get serial-number
```

```
diag gpon get onu-state
```

`omcicli set sn` меняет только OMCI-копию, не серийник PLOAM - им не пользоваться.

#### Режим `LAN_SDS_MODE`

| Значение | Режим |
|---|---|
| `1` | FIBER, 1000BASE-X, автосогласование включено |
| `3` | SGMII MAC, 1 Гбит/с |
| `7` | SGMII Force, 1 Гбит/с, автосогласование выключено |
| `4`, `5`, `6` | режимы 2,5 Гбит/с |

По отчётам: медиаконвертер работает с `3`; MikroTik hEX S - с `1`. **Для карт
Broadcom и других SFP+ данных не найдено**, какой режим нужен - выясняется
только на месте. Порядок: линк на заводском режиме; нет линка - менять режим
**только имея под рукой UART и способ питать стик**. Автооткат режима есть
лишь в модифицированной прошивке из гайда yashau, на заводской его нет.

#### Консоль UART (если стик "пропал" после смены режима)

По hack-gpon: TTL **3,3 В**, 115200 8-N-1, контакты `TX`, `RX` и `GND` на
верхней стороне платы рядом с SFP-разъёмом (метки на USB-TTL иногда
перепутаны - тогда поменять `TX` и `RX` местами). Переходник USB-TTL **стик не
питает**: нужен SFP-breakout или разъём без клетки, либо подключаться к
контактам при стике, вставленном в питающий хост. Нужен ли разбор корпуса, на
странице не сказано.

### 9.6.3 - Подключить оптику и проверить регистрацию

1. вынуть оптический патч-корд из **терминала** провайдера;
2. **терминал убрать** (не выбрасывать - в коробку, это откат);
3. патч-корд через переходник SC/APC-SC/UPC - в стик;
4. на веб-панели или в консоли стика смотреть **состояние ONU**: нужно
   дойти до **O5** (рабочее). Промежуточные O1-O4 - идёт регистрация.

| Состояние | Что значит | Куда копать |
|---|---|---|
| доходит до **O5** | станция приняла стик | дальше п.5 |
| застряло на O1/O2 | нет сигнала / не та длина волны | чистый коннектор, переходник APC, уровень RX |
| O2-O5 по кругу, не закрепляется | слабый сигнал (RX ниже ~-23 dBm) | почистить коннектор, проверить RX на панели стика |
| O5 есть, но интернета нет | не тот серийник/PLOAM, или станция не перепривязана | сверить SN/PLOAM; позвонить провайдеру про перепривязку |

5. когда ONU в **O5** - дальше обычная PPPoE: Шаг 9.1 `prepare --vlan 10`
   (тег из 9.6.1), затем 9.2 `test` и 9.3 `enable`. Интерфейс стика выступает
   как физическая карта `wanphy`, поверх которой поднимается `wan`.

> Если `test`/`enable` упираются в `Timeout waiting for PADO` - проверь, что
> стик именно в **O5**: без регистрации на станции PPPoE-пакеты наружу не
> уходят, и дело не в логине.

### 9.6.4 - Откат на терминал провайдера

Самый быстрый откат на свете: вынуть оптику из стика, вставить обратно в
терминал, включить терминал. Если до этого уже сделан `enable` PPPoE и шлюз
теперь ждёт PPPoE на своей карте, а ты возвращаешь терминал-роутер (он сам
раздаёт DHCP) - на шлюзе ещё и `sudo gw-pppoe.sh disable` (Шаг 9.4).

## Почему так, а не иначе

- **NetworkManager, а не голый `pppd`.** Шлюз уже управляет WAN через
  NetworkManager. С версии 1.10 профиль PPPoE задаёт родительскую карту
  (`pppoe.parent`) и **имя PPP-интерфейса** (`ifname`) отдельно - это и
  позволяет назвать PPP `wan`. В Debian 13 - NetworkManager 1.52.
- **Имя `wan` у PPP.** Иначе пришлось бы менять `wan` -> `ppp0` в NAT,
  фаерволе, `gw-nat`, `warp-pick`, `netwatch`, `bootcheck`... и ошибиться в
  одном из мест. Цена - переименование физической карты в `wanphy`, поэтому
  смена режима идёт через перезагрузку.
- **Страж с откатом.** Без него ошибка в пароле на удалённой точке = шлюз
  без интернета и без Tailscale, приехать некому.
- **`autoconnect-retries 0`.** По умолчанию NetworkManager бросает попытки
  после 4 неудач; для роутера нужно "бесконечно".
- **MTU/MRU 1492.** Заголовок PPPoE занимает 8 байт из 1500.
